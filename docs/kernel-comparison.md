# Kernel and runtime comparison

Source inspection. This accompanies the [kernel capability tables](kernel-capabilities.md) and [full generator inventory](kernel-inventory.md). It is engineering research, not README copy or a performance ranking.

**jitllm's architectural advantage is runtime kernel generation.** It builds CPU machine code and GPU compute kernels for the loaded model's dimensions, layouts and available hardware. The inspected CPU/CUDA paths in ik_llama.cpp and CPU paths in kimi-k3-in-c choose implementations compiled during their builds. Runtime graph assembly and driver compilation are separate from this model-specific kernel generation.

For adoption, that means automatic hardware adaptation, shape specialization without rebuilding the application, and generated alternatives when an optimized path is unavailable. Our GPU generators share an IR across CUDA, Vulkan and Metal. The techniques below are opportunities to strengthen this runtime compiler; comparing named kernel inventories alone misses that advantage. [Our construction paths](kernel-inventory.md#when-and-how-code-is-built), [ik_llama.cpp dispatch][ik-mat], [kimi-k3-in-c kernels][k3-ops].

Snapshots inspected:

- jitllm: working tree based on `b1ce938`, including existing local changes. Kernel generator files are unchanged from the earlier `6517e21` inventory; paging and expert scheduling have advanced.
- [ik_llama.cpp at `1aaf7105be6e`](https://github.com/ikawrakow/ik_llama.cpp/tree/1aaf7105be6e55a97fa4a9fd6f5bd362b08436dc).
- [kimi-k3-in-c at `a2ad8e5982da`](https://github.com/FareedKhan-dev/kimi-k3-in-c/tree/a2ad8e5982daef0237e037e16f29401a63cee57d).

The comparison follows constructors, arithmetic, dispatch and call sites. Neither external engine nor a model checkpoint was benchmarked here. “Gap” means no equivalent production implementation was found in the inspected jitllm paths; it does not mean that our runtime cannot execute the broader operation.

## Execution model

| Project | Kernel implementation | How execution is assembled |
|---|---|---|
| jitllm | CPU native bytes emitted at runtime; GPU IR lowered to PTX, SPIR-V or MSL and compiled/loaded at runtime | Model-specific plans build operations, buffers and sequences; alternative generated kernels replace unavailable specializations. [Construction paths](kernel-inventory.md#when-and-how-code-is-built). |
| ik_llama.cpp | C/C++ CPU kernels and CUDA templates compiled through its build; runtime dispatch chooses among implementations | GGML graph construction, scheduling and fusion, with shape/format-dependent kernel choices. Inspected CPU/CUDA arithmetic is not a native-code emitter like ours. [CPU dispatch][ik-mat], [CUDA build][ik-build], [graph builder][ik-graph]. |
| kimi-k3-in-c | C kernels with compile-time AVX2/ARM NEON branches and scalar implementations; optional OpenMP | Explicit K3 layer execution and memory scheduling in C. Its scalar alternative is compiled C, not runtime-generated native code. [Kernels][k3-ops], [build][k3-build]. |

## ik_llama.cpp: concrete differences

| Technique / kernel | What its source implements | jitllm today | Assessment / adoption value |
|---|---|---|---|
| **Fused Flash Attention** | CPU flash-attention implementations and CUDA vector/tile/MMA families; online maximum, softmax normalization and value accumulation inside tiled attention. [CPU][ik-fa], [CUDA tile][ik-fa-tile], [dispatch][ik-fa-dispatch]. | Generated score kernels, optional tensor-core scores, separate generated softmax and accumulation, including page/window traversal. [Device sequence](../jit/gpu/tier/encoder.go), [kernels](../jit/gpu/kernels/attn.go). | **Optimization gap.** We compute attention already. A generated fused/online-softmax kernel could reduce intermediate traffic and scratch; it must also respect our paged KV and window semantics. |
| **Quantized KV** | CPU FA admits Q8_0, Q8_KV and Q6_0; extra low-bit forms are build-gated. CUDA has quantized KV specializations too. Format pairs and head dimensions have restrictions. [CPU admission][ik-fa], [CUDA dispatch][ik-fa-dispatch]. | Host F32/F16 cache layouts; device F32 K and optional F16 V on the ordinary path. No Q8/Q4 KV codec/attention-reader pipeline found. [Host layout](../engine/model/kvlayout.go), [device tier](../jit/gpu/tier/tier.go). | **Representation and kernel gap.** Lower cache bytes could reduce both resident memory and page transfer volume. Requires storage, attention readers, migration, serialization and accuracy validation together. |
| **Hadamard-transformed KV** | Hadamard kernels and model integration for supported quantized K/V caches; explicit architecture restrictions. [CUDA transform][ik-hadamard], [integration][ik-llama]. | No Hadamard cache transform or corresponding cache plan found. | **Additional quantized-KV technique.** Evaluate alongside cache quantization; a transform alone is not a usable KV mode. |
| **Broader low-bit weight formats** | IQ families, IQK variants, trellis IQ1_KT–IQ4_KT, additional legacy/K formats and interleaved forms have numerical kernels and dispatch. Coverage differs across backends. [CPU dispatch][ik-mat], [trellis implementation][ik-trellis], [CUDA quantized matmul][ik-mmq]. | Eight packed quantized formats: Q4_0, Q5_0, Q8_0, Q3_K, Q4_K, Q5_K, Q6_K, MXFP4. Float paths also exist. Metadata recognizes more formats than packed execution supports. [Format list](../format/quant/types.go), [GPU mapping](../jit/gpu/kernels/quantof.go). | **Compatibility gap.** New formats need decoding/packing definitions and CPU/GPU generation. A generic existing matmul generator cannot infer an unknown encoding. |
| **AVX-512/VNNI kernels** | `HAVE_FANCY_SIMD` selects AVX-512 implementations; quantized GEMM includes 512-bit integer dot and accumulation instructions. [Feature guards][ik-config], [K-quant kernels][ik-kquants]. | SSE, AVX2 with optional AVX-VNNI, and ARM NEON tiers. AVX-512 is probed but not selected as a compute tier. [Tiers](../jit/cpu/tier.go), [dot selection](../jit/cpu/prevnni.go). | **Hardware optimization gap.** Our AVX2 generation provides execution on those hosts; a new emitter tier could use wider vectors/register capacity. Benefits need shape-specific measurements. |
| **Temporary Q8/interleaved expansion for prefill** | `is_dequant_better` uses format/token thresholds; `iqk_mul_mat` converts small weight tiles into an intermediate representation and reuses them across token columns. [Implementation][ik-mat]. | Packed token-tiled kernels reuse unpacked work within their generated tile; no equivalent cross-format Q8 scratch strategy found in `MatMulPacked`. [Packed matmul](../engine/nn/packedmm.go), [emitter](../jit/cpu/packedtiled.go). | **Different optimization strategy.** Worth a prefill experiment where repeated decode costs dominate. `.jlm` already handles persistent layout preparation; temporary numerical expansion is a separate tradeoff. |
| **Up/gate projection plus activation fusion** | `iqk_moe_fused_up_gate` performs paired projections and the activation/multiply through a fused CPU operation. [Implementation][ik-mat], [graph use][ik-graph]. | CPU batches/gathers packed projections and has fused activation-multiply, but gate/up projection results are materialized before `actmulAll`. GPU likewise has expert projections and `ActMul`. [MoE path](../engine/model/moe.go), [GPU elements](../jit/gpu/kernels/elem.go). | **Fusion opportunity, not missing FFN.** Our `PackedFused` name describes a packed matvec strategy; it does not establish full FFN fusion. |
| **FlashMLA** | Flash-attention machinery includes asymmetric/MLA head geometries, such as its 576/512 specialization. [CPU specialization][ik-fa-mla], [CUDA dispatch][ik-fa-dispatch]. | Absorbed/latent MLA with generated projections and separate attention stages on CPU/GPU. [Host MLA](../engine/model/mla.go), `emitMLA` in [device layers](../jit/gpu/tier/mladecode.go). | **Same MLA capability class, different attention implementation.** The relevant gap is fused attention, not absence of MLA. |
| **Fused delta-net** | Dedicated CPU recurrent update and CUDA delta-net kernels. [CPU][ik-mat], [CUDA][ik-delta]. | Generated scalar-decay and channel-decay state-update kernels; layer composition includes convolution, gates and normalization. [CPU](../jit/cpu/delta.go), [GPU](../jit/gpu/kernels/recurrent.go). | **Already present at the operation level.** Exact batching/fusion and model equations must be compared individually; do not count the feature name as wholly missing. |
| **Speculative decoding** | Speculative infrastructure includes multiple proposal strategies, model state/checkpoints and acceptance machinery. [Interface][ik-spec], [implementation][ik-spec-impl]. | No production draft/verify/accept decoding loop found. Existing batched execution and recurrent/KV state management are building blocks. | **Algorithm gap beyond kernels.** Runtime generation does not automatically supply a speculative decoding algorithm. |

Its current README concentrates maintained performance support on CPU and CUDA. That is the project's own support statement, not evidence that its checked-in Metal/Vulkan code is absent. Our PTX/SPIR-V/MSL generation should be described directly, without inferring backend parity from file counts. [Project support statement][ik-readme].

## kimi-k3-in-c: overlap and specific additions

| Technique / kernel | What the inspected code does | Comparison with jitllm |
|---|---|---|
| **MXFP4 without a full expanded weight matrix** | `k3_matmul_mxfp4` reads packed nibbles/scales, decodes within the dot loop, and uses floating-point accumulation. It can widen the activation once for reuse; AVX2 has a flat-row path with double accumulators. [Kernel][k3-ops]. | **Already supported format and execution pattern, different arithmetic.** Our packed MXFP4 kernels combine generated decoding with quantized-activation dot computation. Do not infer numerical identity or a speed winner between these paths. [CPU packed](../jit/cpu/packed.go), [GPU matvec](../jit/gpu/kernels/matvec.go). |
| **KDA recurrence** | Per-channel state decay, delta write and query readout; K3's gate uses `alpha = exp(lower_bound * sigmoid(exp(A_log) * (z + bias)))`. [Kernels][k3-ops]. | **Recurrence exists; this gate formula differs.** Our Kimi-Linear channel-decay path uses `exp(-exp(A_log) * softplus(z + bias))`. Reusing `GatedDeltaChan` is plausible, but the K3 gate and model plan must be implemented explicitly. [Host gate](../engine/model/delta.go), [GPU recurrence](../jit/gpu/kernels/recurrent.go). |
| **SiTU-GLU** | Soft-caps gate/up with tanh, while sigmoid reads the uncapped gate: `b1*tanh(g/b1)*sigmoid(g) * b2*tanh(u/b2)`. [Kernel][k3-ops]. | **Missing activation definition/integration.** We have softcap and sigmoid/multiply primitives, but no current SiTU-GLU activation kind or plan. A new generated composition or fused generator could implement it; it is not already selected automatically. [Activation kinds](../jit/gpu/kernels/actkind.go). |
| **Attention Residuals** | Normalizes prior residual sources for scoring, softmaxes across sources, then sums the raw source vectors. [Kernel][k3-ops]. | **Missing model-level operation/state flow.** RMSNorm, projection, softmax and AXPY primitives exist; a residual-history plan, weights and execution path do not follow automatically from them. |
| **Latent MoE** | Routes at hidden width, projects into an expert latent space, runs expert FFNs there, optionally normalizes the aggregate, and projects back; shared experts remain a separate path. [Kernel/data structures][k3-ops], [interface][k3-api]. | **Additional model composition.** Current ordinary MoE execution does not expose this outer latent down/up pipeline. Projection primitives are reusable, but converter roles and layer planning need explicit support. [Our MoE](../engine/model/moe.go), [layer plan](../engine/nn/device.go). |
| **Expert-major prompt chunks** | Routes a chunk first, fetches each unique expert, computes every selecting token, then reduces contributions in the original top-k order. [Prefill implementation][k3-ops]. | **Already present in principle.** `moeBatch` routes rows first, holds one expert page, applies it to all selecting rows, and releases it. Our accumulation order is ascending expert ID consistently with our decode path. This is not a new paging or reuse capability. [Implementation](../engine/model/moe.go). |
| **Trunk retention plus bounded streaming** | Pins selected dense layers, uses a budgeted ring for the rest, and can overlap reads through a worker. Expert retention uses a separate LRU cache. [Trunk][k3-trunk], [expert cache][k3-cache]. | **Broad capability already present; policy differs.** Our pager prioritizes evicting unpinned expert pages by LRU before dense block pages, and has a separate cyclic-block policy. Layers, experts, KV and recurrent state are already pageable/movable. Compare admission/prefetch policies rather than proposing paging as new. [Weight policy](../format/jlm/read.go), [partial I/O](../format/jlm/partial.go), [KV/state](../engine/model/kvpage.go). |
| **MLA** | In `k3_mla_cached`, the latent is expanded through `kv_b` into per-head cached K/V: allocation scales as `positions * heads * (qk_nope + v_head)`, plus a shared rope portion. [Kernel][k3-ops], [allocation][k3-cli]. | **Not a new compressed-cache technique for us.** Our absorbed MLA keeps the latent representation for attention. The K3 repository's high-level latent description should not be substituted for its actual cached execution layout. [Our MLA](../engine/model/mla.go), `emitMLA` in [device layer](../jit/gpu/tier/mladecode.go). |
| **Incremental state persistence** | CLI save/load carries recurrent/short-convolution state and KV; chat has its own constraints. [CLI][k3-cli]. | **Overlap.** We already store/restore KV and recurrent state for cached prefixes. Exact file/CLI workflows differ. [State persistence](../engine/model/kvpage.go). |
| **N-gram / draft-model speculative decoding** | Draft proposals, greedy batch verification and recurrent-state rollback/replay; optional draft uses a different trunk and resident-only experts. [CLI execution][k3-cli]. | **Missing end-to-end algorithm.** Existing batched generation and stored state help implementation but are not a working draft/verify loop. Their draft restriction is not equivalent to changing the exact model's expert routing. |
| **Reproducible accumulation contract** | Matmul scalar and SIMD paths deliberately align reduction order and double/FMA arithmetic, with comparison tests. [Kernels][k3-ops], [build flags][k3-build]. | **A numerical design choice, not a universal performance optimization.** We have numerical/dispatch tests and generated float/int8 arithmetic; borrowing their FP64 contract would change throughput and numerical behavior. |

The project's small-RAM demonstrations are its reported measurements. They do not establish jitllm throughput or a CPU-to-GPU comparison. Its own detailed performance notes distinguish a resident **trunk** from the much larger expert store and report speculative-draft speed limitations. We did not reproduce those measurements. [Detailed report][k3-speed].

## What is worth investigating next

These are source-based recommendations, not measured wins for jitllm:

| Candidate | Why it could matter | First useful experiment |
|---|---|---|
| Generated fused/online attention | Affects an existing operation across many supported models; avoids separate score/probability traffic | Compare a generated tiled fused kernel with our existing sequence at decode and prefill shapes, including paged KV, masks, windows, GQA and sinks. |
| Quantized KV, then optional Hadamard | Reduces resident cache and potentially page-transfer bytes | Add one explicit cache format end to end; test accuracy and page round trips before extending formats or transforms. |
| Up/gate/activation fusion | Can reduce intermediate writes and scheduling/launch overhead in existing FFNs | Fuse one common packed FFN shape while retaining the current generated composition as the comparison path. |
| AVX-512 emitters | Uses hardware resources our current tiers leave unused | Add one representative packed matmul emitter and compare register pressure, throughput and host frequency behavior. |
| Additional weight encodings | Unlocks models distributed in unsupported direct-compute formats | Select a format based on actual adoption demand, then implement packing, CPU/GPU generation and numerical fixtures. |
| Temporary expanded prefill tiles | Might amortize decoding across many prompt columns | Compare our direct packed token tiles with bounded Q8 scratch expansion, including conversion cost and total memory traffic. |
| K3 model support | Requires multiple specific equations, weights and state flows, not just MXFP4/KDA availability | Map SiTU-GLU, bounded decay, latent MoE and Attention Residuals into conversion/plans; validate against a small reference before claiming compatibility. |
| Speculative decoding | Could amortize expensive weight reads over accepted tokens | Measure proposal acceptance and total bytes/time including rejected-batch replay and recurrent-state restoration. |

Existing paging, expert-major prefill, MLA, recurrent state updates, runtime hardware selection and generated fallback computation belong in the **already implemented** column. New optimized kernels can improve their cost without being prerequisites for executing those operations.
