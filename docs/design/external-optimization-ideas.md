# jitllm optimization research: tuning and model extensibility

These are proposals and source-inspection findings, not measured speedups or binding project rules. Read `AGENTS.md` first; it governs implementation and validation. Recheck the named code against the implementation checkout before changing it.

**Overall research target:** minimize TTFT and maximize generated-token rate for each supported workload while preserving jitllm's five principles. Make a new model built from known operations a small, predictable converter addition, and make a new optimization technique a similarly contained compiler addition. Also reach the ability to run an unknown-to-jitllm model from a verified executable graph and improve it with the same composer and JIT. Pursue that capability without sacrificing the performance and extension costs above. The Magnitude experiment below is one narrower tuner experiment. See [Performance-led model extensibility](#performance-led-model-extensibility).

### Three optimization stages

**User direction:** optimization happens in three places, connected by the same graph, representation and recipe contracts:

| Stage | Inputs and decisions | Output and validation |
|---|---|---|
| Offline, during conversion | Verified model semantics and immutable weights. Canonicalize graphs, prove legal rewrites, remove provably unused work, compress eligible pages, and prepare portable layouts and metadata. Device-dependent alternatives remain candidates. | Versioned graph and weight representations with guards and numerical contracts. Validate semantics and exact codec recovery. No executable kernels are stored. |
| Runtime, during emission | Actual device capabilities, encoded weights, shapes and initial budgets/residency. Choose compatible combinations of layouts, fusion, tiling, reductions, schedules and decoding; emit the selected plan. | Generated kernels and prepared bindings/scratch/captures, with a correct generated baseline and bounded preparation cost. Hardware qualification is scoped to the actual plan and workload. |
| Continuous, through autotuning or profile-guided optimization | Counters and performance measurements from execution: row/context classes, page faults, bytes moved, residency changes, waits and relevant device resource observations. Detect when the current plan is mismatched, construct candidate combinations, and measure them under controlled conditions. | Reuse a qualified variant or replan and re-emit kernels for the observed conditions. Invalidate dependent captures/bindings, switch safely and retain a compatible prior/generated plan for rollback. Charge observation, trials, emission and recapture costs. |

Continuous optimization changes generated code when the evidence warrants it; it is more than selecting fixed kernels. It need not re-emit on every counter change: use bounded observation, minimum evidence and hysteresis to prevent oscillation. Record the profile scope and plan version so evidence cannot silently apply to a different layout, device or workload. Passive counters identify candidates; uncontrolled live timings alone do not establish causal speedups. State-changing trials remain isolated/restored, and instrumentation must respect warm allocation and no-Go-compute requirements.

The stages compose. For example, conversion compresses and indexes weights; emission fuses the appropriate decoder into a consuming recipe; continuous observations can change tile size, fusion boundaries, prefetch or placement and trigger re-emission. Changing a runtime plan does not invent an unavailable offline representation or require recompressing the checkpoint. Offline transformations must retain enough semantics and metadata for later legal choices; each plan records which stages contributed its levers. End-to-end acceptance measures the combined result and its preparation/adaptation costs.

### Persistent optimization evidence per block and target

**User direction:** offline conversion artifacts already persist. Continuous optimization must also persist qualified wins and clear losses so future sessions, model instances and relocated blocks reuse the evidence instead of repeating the same experiments. The unit of application is a block on a target device under a workload/residency class; a multi-block recipe additionally records every participating block and its co-placement/state guards.

Separate a **block binding** (model/artifact, block identity, current device and representation) from a **reusable tuning key**. The latter describes the semantic region/pattern, dimensions, numerical contract, quantization/codec/layout versions, candidate combination and pass order, target hardware capabilities, relevant driver/compiler/runtime versions, row/context class, budget/residency class and measurement objective. Include weight identity or measured weight-dependent properties when they affect the decision. Do not assume equal dimensions make blocks equivalent. Equivalent blocks/instances can share evidence only when these cost- and correctness-relevant properties agree; bind current addresses separately.

| Persisted outcome | Future behavior |
|---|---|
| Qualified winner | Prefer its plan/recipe within matching guards, re-emitting executable kernels for the actual target and binding current pages. Persist decisions/evidence, not pregenerated kernels. |
| Clear measured loss | Suppress repeating that exact candidate-plan comparison within its validated scope. Retain the control, raw evidence, uncertainty and relevant versions. |
| Unresolved/noisy/insufficient evidence | Preserve the record without classifying it as a loss or using it to eliminate candidates. |
| Invalid/unsupported candidate | Record the violated legality/capability guard separately from a timing loss; reconsider when the guard or implementation changes. |

A losing isolated lever does not blacklist combinations containing it. Negative evidence applies to the tested complete plan, ordering, workload and device; an enabling lever can still participate in a winning bundle. Changes to semantics, representation, lowering, device stack or workload invalidate affected verdicts. Define bounded revalidation for drift rather than treating a loss as permanent universal truth. Historical evidence guides selection and avoids redundant exploration; new comparative performance claims still require fresh baselines under AGENTS.md.

On relocation, resolve the block's destination binding, look up compatible destination evidence, and use its qualified plan when available. A source-device win or loss is not a destination verdict. Without matching evidence, start with a legal generated plan and schedule bounded qualification; relocation correctness cannot depend on waiting for a tuning experiment. Page/address changes invalidate affected captures and bindings even when the reusable tuning decision remains valid.

Coordinate discovery across instances with an atomic claim/lease keyed by the exact experiment scope, plus atomic publication of versioned records. A per-process map is insufficient. Other instances use a qualified/generated plan while one owner tunes; stale claims can expire after failure. Recheck for published results when acquiring a claim. Include execution isolation and contention conditions in experiment eligibility so a shared result is not measured under accidental competing tuners. Cross-host sharing needs an explicit common store and compatible environment identity; a local cache cannot guarantee fleet-wide deduplication. Existing valid evidence prevents routine duplicate trials, while deliberate revalidation remains possible.

The evidence store is advisory: missing, corrupt, stale or incompatible records fall back to legal generated execution. Keep lookup/locking/publication outside the warm token hot path, bound storage, and preserve zero warm allocations. Counter collection can remain lightweight; preparation and cache I/O costs belong in lifecycle measurements.

### Multiple generated variants and profile-guided offline preparation

Keep multiple compatible kernel/block versions available: persistent recipe/evidence records describe alternatives, an in-process generated-code cache holds emitted variants, and execution plans bind variants to pages, scratch and placement. Decode/prefill widths, target devices, fusion, tiling and available compressed/plain representations can select different versions. Bound each cache and retain active variants until their users finish. Compatible instances can share code, but session-specific bindings, mutable state and captures require separate ownership. After restart, persisted recipes still produce runtime-emitted executable code.

**Optional later feedback loop (user proposal).** Measurements accumulated across runs may eventually justify revisiting offline optimization. This is profile-guided artifact preparation, not model training or an assumed performance win. Candidate changes include compression tile/index choices, portable weight layouts, page grouping that preserves independent access, or legal graph/representation alternatives that are too expensive to rebuild during a request. Profiles need artifact/block identity, recipe versions, device/workload/residency classes, sample counts and uncertainty. Aggregate by these classes; mixing incompatible profiles can optimize the wrong workload. Preserve generic compatibility or label a specialized artifact's intended scope explicitly.

In interactive use, offer a concrete re-optimization proposal when evidence supports it: observed bottleneck, proposed transformation, estimated resource cost and expected benefit with uncertainty. Perform it after user approval. In server mode, a separately configured maintenance policy can authorize scheduled jobs when the model is expected to be cold or compute, I/O and temporary storage budgets permit. Predicted coldness is a scheduling hint, never permission to evict live state or delete an in-use artifact. Jobs yield or stop at bounded checkpoints when foreground demand returns, and do not compete with controlled measurements.

Write a new versioned artifact from the source/existing losslessly recoverable representation; never mutate an artifact being served. Budget source, old artifact, new artifact, scratch and validation space together. Validate semantic/codec equivalence and required execution behavior, then measure complete-request benefit including amortized preparation before promoting a performance claim. Publish atomically for future loads, retain rollback and pin old versions while sessions use them. Live sessions continue with their current version unless a separately verified migration path exists. Changed representation/graph versions invalidate affected tuning evidence and plans; carry forward only records with demonstrated compatibility. Coordinate maintenance across instances to avoid duplicate rebuilds.

Prioritize this only after profiles reveal a repeatable benefit unavailable through emit-time or continuous plan changes. Earlier compiler work needs stable profile provenance and representation versions, not an immediate background conversion scheduler. Record failed/no-benefit offline experiments as scoped evidence too. This closes a possible loop: conversion -> emit -> observe/tune -> propose or schedule a new conversion artifact.

### Model exceptions become compiler shapes

**User direction:** as the compiler matures, exceptions currently expressed as model-family special cases should be described as compiler shapes. Here a shape means a recognizable computation pattern and its semantic constraints, not only tensor dimensions. It includes operation order and connectivity, dimensions and layouts, numerical contracts, state effects, and the guards under which a lowering or optimization is valid. Device capability and residency are additional plan guards, not model identity.

For example, recognize projection -> per-head norm -> rotary separately from projection -> rotary -> per-head norm; represent gated versus ungated FFNs, shared versus independently owned KV, and grouped top-k routing with its scoring and normalization explicitly. The optimizer matches these properties rather than asking whether the model is Qwen, Hunyuan or DeepSeek. One model can contain several compiler shapes, and unrelated families can share the same shape.

A targeted optimization therefore contributes a pattern, legality/numerical guards, generated candidate recipe and counterexamples that reject near-matches. A new composition of existing semantics adds a reusable pattern or decomposition; a genuinely new operation adds a semantic primitive and BASIC generated lowerings. Neither case should be hidden behind an opaque family callback. Unmatched optimized patterns retain the correct generated BASIC plan for supported semantics; unsupported semantics are refused. Frontend family knowledge can still resolve source defaults and bindings, but it must become explicit graph facts before optimization and execution planning.

Migrate existing exceptions incrementally when their subsystem is covered: first make the distinction explicit in the graph, then verify positive and near-miss matches, then replace the runtime family check. Do not erase distinctions merely to canonicalize two graphs into the same shape. Acceptance includes applying a pattern to a second eligible graph and showing that an ineligible neighbor is rejected. This keeps targeted fast paths available while turning their applicability into reusable compiler knowledge.

### Intended end state and implementation base

jitllm already emits kernels at runtime; the proposed change makes more of the manually prescribed model graph, operation composition and execution schedule compiler-derived. The target pipeline is: read weights plus verified model/input/state semantics -> validate a computation graph -> discover legal optimizations -> choose representations, partitions, placement and recipes -> emit for the actual hardware -> adapt to workload, residency and budgets. A new combination of supported operations should reuse this machinery without a family-specific executor. A genuinely new primitive still needs semantics and generated lowerings; weights alone cannot reveal those semantics. Each eligible model should inherit accumulated optimizations, and each new optimization should be reusable across eligible graphs.

Performance leadership in TTFT and tok/s is the competitive objective, not a guarantee of generic compilation. Cold preparation costs, bounded search, workload-specific choices and strong same-pass baselines remain part of that objective. Unknown-architecture execution means a complete verified graph whose semantics the engine supports, under the existing admission gates.

**Implementation base:** start from current main and extend its existing composer (`docs/design/composer.md`, `jit/gpu/tier/recipe.go`); no separate composer branch is needed.

## Recommended roadmap: reusable optimizations with fewer hardware iterations

This roadmap orders the experiments below; their section-local rankings are priorities within a workload, not competing global implementation sequences. The objective is to reduce debugging and redundant searches on scarce target hardware while retaining every required correctness and performance gate. Hardware-independent validation cannot certify device synchronization, floating-point behavior, occupancy or throughput.

The [implementation-agent harness](optimization-agent-harness.md) supplies a structured task contract, stage gates, candidate/evidence ledger, interaction tests and final handoff format. It is a specification for wrapping the existing runners, not a claim that an executable harness has been implemented. AGENTS.md remains the binding rule source.

**Optimize combinations toward the goal (user direction).** The search unit is a complete execution plan, not an individually winning lever. A lever that regresses in isolation may enable a profitable combination: compression plus fused decoding plus fewer evictions, or partitioning plus fusion that removes partial-buffer traffic. Keep such enabling candidates in the bounded search, express prerequisites/conflicts and pass ordering, and evaluate legal bundles against the control with ablations. Do not multiply isolated speedups or prune every locally slower prefix. Judge adoption by the complete plan's whole-request performance and all required correctness/resource gates; do not ship an unconditional regressing intermediate path. Missing interaction measurements remain unresolved, and bounded search does not establish a global optimum.

| Stage | Deliverable and bounded scope | Exit evidence | Hardware use |
|---|---|---|---|
| 1. Make experiments reproducible | Extend existing check/harness infrastructure with a manifest of graph/recipe revision, shapes, quant/layout, state, placement/budget and workload. Emit plan explanations and deterministic counts; retain small failing fixtures. | Reproduce an existing issue from a saved manifest; identify exactly which variant executed. | Reuse existing traces to design experiments. Historical timing guides selection, never supplies a new comparison baseline. |
| 2. Establish one shared semantic slice | Represent two existing dense block variants and their state effects, then lower through current generated operations. Define logical weights separately from their physical encoding and residency. | Independent reference values, shape/effect verification and round-trip checks pass; the selected slice has one semantic definition across decode/batch/backend plans. | Run required backend and principle gates and a same-pass regression comparison before extending coverage. Keep the old path as a temporary control. |
| 3. Establish the optimization extension interface | One recipe/rewrite declares its graph match, legality guards, numerical contract, resource requirements, effect changes, dependencies and candidate construction. Start with one existing fusion plus an unfused generated control. | One implementation applies to both covered graphs; deliberate invalid matches fail; plans explain acceptance/rejection. | Test only legal candidates, then compare complete recipes and requests. Add joint split/prologue tuning through this interface. |
| 4. Make search and validation incremental | Track which passes, lowerings, layouts and captures depend on each artifact. Deduplicate equivalent regions by cost-relevant keys; bound candidate search and preserve a legal default. | A change identifies affected candidates and tests; unrelated artifacts remain reusable. Tests catch stale keys and invalidation. | Use `scripts/checks` required gates; targeted exploration avoids unrelated sweeps. New architectures still run all their admission gates. |
| 5. Prove reuse on a second optimization | Select from row-demand pruning, norm/gate fusion or page-demand scheduling using existing workload evidence. Reuse the graph/effect and recipe contracts rather than adding another executor. | The technique works on a second eligible graph; report files/branches changed, preparation cost and measured whole-request effect. | One relevant workload first, then required scope coverage. Small fixtures find errors before large-checkpoint runs. |
| 6. Add compressed representation support | Sample actual page compressibility offline first. If worthwhile, encode pages at conversion, describe them in the container, and select generated fused decoders at load. | Bitwise page/tile recovery, bounded indexing/scratch, mixed plain/compressed pages, generated backend coverage and correct relocation. | Compare under identical budgets and relocation traces: no evictions, compression prevents evictions, both still evict. Include decoder, load/JIT and scratch costs. |
| 7. Expand scheduling and model intake | Add joint fusion/partitioning and bounded prefetch where traces show opportunity. Broaden graph semantics as needed; import an approved unknown class from a complete verified graph. | A new model using supported operations needs no family runtime path; a new optimization reuses the same extension interface. | Whole-generation persistence follows only when its resource and synchronization costs can be tested against a strong captured baseline. |

Stages 1–3 are a thin vertical implementation, not a prerequisite to migrating every model or designing a universal compiler. Compression sampling and existing independent serving fixes can proceed without waiting for graph migration; integrating their runtime effects should use the shared contracts as they become available. Stop expanding an abstraction until one real optimization and a second graph exercise it.

### Validation ladder and hardware scheduling

1. **Before target execution:** validate shapes, effects, aliases, state ownership, page bounds, guards and serialization; perform exact codec round trips; compare semantic transformations with independent reference fixtures. A test-only evaluator may help test graph semantics but is never a production Go fallback. Static resource estimates filter candidates conservatively; they are not actual occupancy measurements.
2. **Small target fixtures:** execute forced generated variants, edge tiles and numerical boundaries. Test synchronization and relocation directly on the affected backends. Preserve the failing input and emitted variant so the next hardware session starts with a reproduction.
3. **Bounded recipe experiment:** establish A/A control, then paired/interleaved complete-recipe measurements under the project's sample and repeat requirements. Search representative shape/format classes before extending coverage; do not prune solely because a speculative cost model predicts a small gain.
4. **Whole-request confirmation:** measure TTFT, tok/s, memory, allocations and traffic on the affected workload against a freshly measured baseline. A kernel win alone does not select a production plan. Run the required architecture and five-principle gates before calling support complete.

Batch target jobs into serial hardware sessions with all fixtures and candidate binaries prepared beforehand. Abort dependent performance runs when correctness fails; missing hardware remains an unmet gate. Cache correctness artifacts and tuning evidence under precise version/device/workload keys, but obey RULE 1 for every new comparative claim: a cached historical baseline is not a fresh baseline. A cost model narrows search; hardware selects the winner. State-changing trials use isolated/restored state and comparable residency.

**Track engineering cost too:** target-device minutes per accepted change, number of candidate trials, failing cases found before device execution, files/runtime family branches added per model, and optimizations reused by another graph. Pair those with TTFT, tok/s and preparation cost. The desired result is a verified common interface that makes each subsequent feature cheaper, without weakening performance or coverage requirements.

## Earlier scoped work: Magnitude's tuning ideas, adapted to the converter

The user suggested placing the structural work in the converter. Treat that as the preferred starting point: determine graph facts and legal alternatives there, while leaving device-specific generation and measured selection to runtime. This division is a proposed jitllm design, not a claim that Magnitude uses our converter architecture.

**Scoped tuner experiment: jointly select split/reduction and operand-prologue fusion for one existing eligible projection site.** Today `jit/gpu/tier/split.go:592` calls `tuneActIn` after splits settle. `jit/gpu/tier/actin.go:21` builds prologue variants using the selected `m.split` and `m.group`. This sequential selection can miss a fused variant whose best split differs from the unfused winner. That is a hypothesis to test, not an established regression.

Magnitude explicitly explores structural forms before refining local parameter choices. Read the executable loop in [native/tune.rs](https://github.com/magnitudedev/magnitude/blob/1f54d5b7e871aff1d1ae276d6a7cc3a3553baabf/inference/seismic/runtime/src/native/tune.rs#L6680), and the actual variant declarations in [dense_rows.seismic](https://github.com/magnitudedev/magnitude/blob/1f54d5b7e871aff1d1ae276d6a7cc3a3553baabf/inference/engine/kernels/kernels/dense_rows.seismic#L96). The latter include algorithm forms, packing, batch crossovers and launch dimensions. This is bounded search over authored alternatives, not evidence of arbitrary kernel synthesis or a globally optimal search.

### Bounded implementation of the tuner experiment

1. Read `docs/engineering-history/gpu-kernels.md`, `docs/engineering-history/scheduling-and-measurement.md`, `docs/engineering-history/placement.md`, and `docs/open-questions.md`. Read model-correctness history before changing graph interpretation, and relevant container designs before changing the format.
2. Trace how conversion records normalization, projection, quantization and graph semantics. Identify one currently supported eligible norm/projection pattern. Reuse existing container facts if they already express eligibility; do not add a format field merely to duplicate facts. Converter recognition must preserve biases, epsilon, activation-window semantics and all current legality exclusions.
3. Represent a small set of legal alternatives, with a device-independent description if conversion needs to record anything new. Keep actual device feasibility checks at runtime. Do not serialize generated kernels, device pointers, or a universal winning configuration into the model.
4. At runtime compare a bounded cross-product of existing split candidates, valid reduction strategies and fused/unfused prologues. Start with one site; preserve the current sequential selection as the control. Time the complete required pipeline, including separate input preparation and reduction where applicable. Reuse actual same-shape weights from different layers, as the existing decode tuner does.
5. Install a winner only for the device and executed shape it was qualified for. Keep the existing generated legal path when tuning is unavailable or inconclusive. Rebuild/invalidate dependent kernels and captured graphs consistently; relocation must select for the destination device.
6. Add correctness tests that force each alternative to execute, plus a controlled-selection test where the best split changes with fusion. This tests search coverage without asserting a machine-dependent speed floor. Verify serialization compatibility only if the format actually changes.

**Acceptance evidence:** compare values against the existing path/oracle, including supported bias/window cases; show the chosen combination actually executes; check paging, partial placement and relocation; preserve zero warm host allocations. Report preparation cost, kernel/cache residency, scratch, traffic, launches and registers/spills as well as whole-token timing. No timing win is assumed. A change in reduction order needs appropriate numerical gates, not only matching greedy IDs.

For this scoped tuner experiment, the deliverable is its bounded trial and result. If existing metadata already carries the graph facts, its patch may be runtime-only; explain that finding rather than forcing a converter change. The separate unseen-model target below requires a generic graph-capture and lowering path.

## 1. Skip unused prompt rows through KV-sharing tails

**Source mechanism.** Magnitude's `inference/engine/executor/src/programs/native_target_graph.rs:766`, `stateless_tail`, walks backward over attention blocks whose history belongs to another layer and which publish no draft taps. `native_target.rs:1113` actually applies the result: it stops execution when no output rows are consumed, or slices the residual and controls to the readout's row window. This is executable dead-work elimination, not a kernel speed claim.

**jitllm gap.** `format/jlm/config.go:740` already recognizes this architectural case through `KVShared`/`KVSource` and `NKVShared`. But `engine/model/prefill.go:623` traverses every block for the chunk, passes `n` to `hostRows` at line 845, and `hostRows` runs the FFN over those `n` rows at lines 1510–1580. Only after all blocks does prefill select the last residual row at line 864. Device execution likewise carries its row width through the FFN in `jit/gpu/tier/layer.go:8385` onward. I did not find a corresponding stateless-tail row filter on these paths.

**Implementable change.** Compute required output rows separately from rows required to update history. On an ordinary causal prefill with no hidden-state consumers, KV-producing blocks still process every row. Once the final state-free KV-sharing run starts, intermediate chunks need no tail output and the final chunk needs only its last row. Support a row set for verification, embedding output, MTP catch-up/rowTap, deepstack or other consumers; never infer “only last row” from prefill alone. Begin with text generation on the existing KV-sharing families.

**Deterministic saving.** For a prompt of P rows and T eligible tail blocks, ordinary final-row-only prefill changes tail row-block work from P*T to T. That is not a P-fold model speedup: all earlier state-producing blocks still run, and a one-row tail uses different kernels. The saving can be counted before measuring time. The final ordinary layer's stateless FFN is another, smaller application even without shared KV, but requires splitting the layer's state-producing and pointwise work.

**Validation.** Compare subsequent decode logits and full live KV against unpruned prefill, not just the first token. Test chunk boundaries, different output-row sets, shared-window attention, partial device placement, paging and relocation; demand execution counters fall only in the eligible tail. With MTP taps or embedding outputs requested, ensure the required rows survive. Rows of per-layer embedding inputs must follow the same selection.

**Costs.** Arithmetic/traffic and coordination improve by construction for omitted work. Selection/plan storage increases slightly. Time, one-row kernel efficiency, and changed reduction order are unresolved. This is my first prefill experiment.

## 2. Keep the complete MTP input path on the device

**Source mechanism.** Magnitude's `inference/engine/kernels/kernels/cuda/draft_rows.cu:35` (`draft_join`) loads the embedding, normalizes it and the conditioning hidden state, and its `draft_rows` entry projects the joined vector. `draft.seismic:65` wires CUDA launch shapes; `programs/native_head.rs:681` enqueues that entry with device tensor ports. Minnie independently runs the same operations on CUDA in `src/server_single.cpp:2351`, although with more separate launches/copies.

**jitllm gap.** `engine/model/spec.go:486`, `draftRows`, calls `embedMTP`, two host JIT RMS norms, and `d.mm(sp.ze, w.ehProj, sp.eh, n)`. `engine/model/prefill.go:960` confirms this `mm` is the host JIT's MatMul/MatMulPacked path. Only then does `d.stepRows` enter the placed prediction block. `rowsOut.hidden` also requests host hidden-state destinations. Thus a GPU prediction block still has a host arithmetic stage in front of every proposal/catch-up call.

**Implementable change.** First add a generated device MTP-input operation using existing embedding, norm and projection machinery; use the existing generated host path when the prediction block is home. Then retain target conditioning and draft hidden rows as device-owned session buffers across rounds, so the host need only inspect proposal/verification token IDs. This second stage requires explicit lifetimes across target and draft calls, not an unowned pointer to reused scratch.

Do not copy Magnitude's fusion literally: its one-row CUDA form recomputes the joined norm in every 32-output group and uses 8*D bytes of shared memory. Existing separate generated operations are a useful control; fuse only where resource cost pays.

**Validation/costs.** Extend `TestMTPMatchesReference`, `TestSpecGreedyOnDevice`, and partial-acceptance fault gates. Include catch-up and head placement on another device; move the prediction block home and back mid-session. Count host projection calls, transfer bytes, synchronizations and device scratch. Host work/link traffic can decrease, device residency grows by the preparation weights/scratch where not already resident. Whole-round benefit is unresolved, and may be limited by the full-vocabulary draft head.

## 3. Device rollback checkpoints instead of replaying accepted rows

**Source mechanism.** Minnie's `src/cuda/activations.cu:5804` writes intermediate recurrent states directly from the scan for m=0 and m=1. Its convolution counterpart carries intermediate conv states too. `src/server_single.cpp:3822` calls `commit_target_state_slot(accepted)`; the function at line 5004 performs D2D copies. The nearby “zero-overhead” comment is false literally: there are actual copies.

**jitllm gap, and correction to the first report.** jitllm already keeps recurrence on chip: `jit/gpu/kernels/recurrent.go:1031–1056` updates register phi values inside the token loop and stores final state only after the loop; `tier/rows.go:1542` chooses the fused run form. Reimplementing that using shared memory would not remove intermediate state traffic that already is absent.

What is missing is selecting an intermediate device state. `engine/model/spec.go:350` chooses replay for device linear blocks and refuses per-row snapshot mode there. On rejection, lines 724–759 rewind to the pre-pass mark and append accepted rows to replay debt; another rejection with debt runs an extra no-head commit pass. `tier/recpool.go:665` only supports returning to the mark by flipping the two halves.

**Implementable change.** Let the existing generated scan optionally write bounded checkpoint slots at verification boundaries, preserving F32 arithmetic. Carry matching convolution and other recurrent tail state. Select the accepted prefix's slot on rejection, with a copy or slot ownership transfer, and discard rejected checkpoints. Extend the session's recurrent-state contract rather than bypassing the pool.

**Cost model.** One F32 delta snapshot is `4*VHeads*VDim*KDim` bytes per linear block, plus conv/tail state. At 48 heads and 128x128 that is 3 MiB per block per checkpoint; two checkpoints across 40 linear blocks would be 240 MiB before other state. This is an illustrative geometry, not an observed jitllm workload. Compare checkpoint writes/VRAM against replayed full-model rows and extra commit passes. A bounded small-draft implementation can choose replay when snapshots do not fit.

**Validation.** Force every acceptance boundary and compare the next several logits; corrupt checkpoint selection and require the gate to fail. Test independently interleaved sessions, all recurrent state components, relocation, shrinking budgets and zero warm allocations. Kernel scan/fused-chain gates alone cannot catch wrong checkpoint ownership.

## 4. Share work among requests arriving in the same prefix burst

**Source mechanism.** Superfluid's `crates/superfluid-daemon/src/scheduler.rs:1706`, `awaits_a_shared_prefix`, compares queued tokens with active lanes and holds eligible followers. It has priority exemptions, a minimum prefix and a bounded hold. `admit_from_queue:2140` actually calls it. `plan_prefix_checkpoints:1760` chooses shared boundaries from the waiting requests and `publish_prefix_checkpoints` saves there for recurrent runtimes.

**jitllm gap.** `server/batch.go:1120` calls `RestorePrefix` before `lp.submit`. `admit:456` considers capacity, room and parked rows but never retries cache restoration for a new waiting row. `ran:1038` publishes the completed prompt using `SealPrompt`. Therefore requests that all miss the cold cache before queueing do not revisit it when a predecessor publishes the prefix. `server/ttft_test.go:102` tests reuse sequentially, which cannot expose this burst case. jitllm already has fairness, parking, priority and adaptive prompt budgets: those are not missing features.

**Implementable change.** First recheck the cache at admission for a still-fresh, unrun cache-miss row. Then add a bounded prefix-producer/follower policy, so a cold simultaneous burst need not start duplicate producers on every lane. Distinguish model/cache namespace, token IDs, image/rotary identity and compatible state layouts. On producer cancellation/failure promote a follower; let unrelated and urgent work proceed.

`RestorePrefix` requires position zero (`engine/model/kvpage.go:1459`): a row with a partial prior restore needs an explicit safe reset/re-restore or extension API. It is not legal simply to call it again on every queued row. Restore placement also affects admission's KV-room accounting. The engine already captures recurrent summaries at eligible page boundaries; the new idea is demand-driven boundaries and joining in-flight work, not inventing recurrent snapshots from scratch.

**Validation/costs.** Concurrent same-prefix requests plus distinct-prefix controls; assert computed prefill tokens, restoration, identical continuations and cancellation behavior. Measure p99 TTFT and unrelated-request starvation, not just aggregate throughput. Duplicate compute improves for followers; queue bookkeeping and checkpoint traffic grow, while follower latency has a wait-versus-recompute tradeoff.

## 5. Make wrong prefetches yield to actual expert demand

**Source mechanism.** Ironbark's `crates/ironbark-experts/src/store.rs:348` dequeues demand before prefetch. Its per-expert Loading/Ready state and pin ownership let a wait target one expert. There are caveats: `request` returns if an expert is already indexed, so an existing queued prefetch is not visibly promoted there; and `claim` can evict an unpinned Ready slot for a prefetch. Copy the scheduling idea, not all its policies.

**jitllm gap.** `jit/gpu/tier/layer.go:411` waits for the entire prediction batch (`pfWG.Wait`) before issuing actual selected reads. `prefetchSelected` calls `ensureBlockSelected`, which starts a goroutine per selected expert and waits for all of them (`engine/model/model.go:2164`). Each page can fan out again in `format/jlm/read.go:654`. Thus one slow wrong prediction can delay issuing a missing demanded expert, even though it is not needed by the token. The whole-batch join is currently a lifetime safeguard.

**Implementable change.** A bounded read service with per-page in-flight records, demand promotion, and page leases lasting through each read/consumer. Wait only on required pages; abandon unstarted wrong guesses. Bound speculative occupancy so it cannot consume every reader or evict the useful working set. Reuse preallocated request slots on warm paths.

Simply deleting the join is incorrect: `EnsureRanges` currently permits concurrent duplicate reads, and the existing join protects frame lifetime. The asynchronous page ownership must be changed with it.

**Validation/costs.** Inject one slow unused prediction and one demanded miss; demonstrate demand issues/completes without waiting for the unrelated read. Test no duplicate page read for overlapping demand, eviction during I/O, cancellation/Close and read errors. Record demand-wait time, wrong bytes, queue depth, allocations and hit rate. Coordination metadata grows; critical-path waiting and duplicate reads should shrink in the targeted schedule, but throughput at NVMe saturation is unresolved.

## 6. Fuse the recurrent output norm and gate

**Source mechanism.** Minnie's scan computes output RMSNorm and z-gating before writing output (`activations.cu:5820` onward). Its one-workgroup-per-head layout makes that possible, but uses BF16 state and atomic reduction steps; those arithmetic/resource choices are not a drop-in replacement.

**jitllm gap.** `tier/layer.go:10620` launches `bs.outNorm` to write `dOutN`, then `outActMul`/`outSigMul` to read it and write `dAct`, then quantizes. The current scan distributes state rows across subgroup owners, so fusing the norm into the scan itself requires a new cross-row reduction layout.

**Smaller first change.** Extend the generated HeadNorm operation with an optional SiLU/sigmoid-times-z epilogue. Keep the current scan, F32 state and reduction order. This removes one launch and the normalized intermediate's write/read: logically `8*rows*VHeads*VDim` bytes, before cache effects, while the required z/norm reads remain. Quantization fusion is a separate step because its grouping differs.

Gate against the existing chain for both gates and all supported widths/backends, inspect registers, and measure full hybrid tokens. This is a contained composer-friendly operation with a shape and explicit epilogue, not generic persistent-block fusion. Arithmetic rounding must be kept explicit if the compiler would contract formerly separated operations.

## 7. Tune GEMM choices by executed row width

**Source mechanism.** Magnitude's `dense_rows.seismic:119–164` contains distinct launch branches for one row, two rows, several small rows and matrix-unit batches; `native/tuning/workload.rs:111` includes prepared verification widths as separate objective terms. Its workload code also fixes concurrency to one and equally weights selected short/long contexts, so “tuned for every workload” would overstate it.

**jitllm gap.** `tier/gemmtune.go:34` measures at `W := g.promptW`. The persistent cache key includes W, but the live winner map is `map[splitKey]bool`, where the key contains quantization, matrix rows and K only. `tier/rows.go:1104` consults that same winner for arbitrary `ntok`. The shape's first tuned width consequently influences other widths without measuring them.

**Implementable change.** Key a winner by the row class actually executed, and compare complete activation-conversion + GEMM + reduction cost at representative widths (verification and prompt/tail classes separately). Cap preparation cost and reuse static legality/resource filters. Keep current heuristics as the default for untimed classes. This does not require adopting Magnitude's compiler.

Do not propose generic weight rotation as new: jitllm's `retuneDecode` in `tier/split.go:452` already times different layers' real weights; `tuneActIn` does too. `timeGemm` currently repeats one matrix, which can be examined separately if cache residency affects its decisions.

**Validation/costs.** Test class-specific cache keys/selection with controlled timing hooks, then paired whole-prefill and speculative-round experiments. Inspect tile spills and scratch as well as latency. Runtime dispatch remains a lookup; preparation time, cache entries and kernel residency increase.

## Secondary candidate: compact draft vocabulary

Minnie's `tools/build_draft_vocab.py:23` selects special IDs and then fills from low token IDs; it does not measure token frequency despite its comment. `server_single.cpp:2453` selects the compact head and line 2471 maps the winning index back. jitllm's `newStateRange` selects the MTP head but retains full-vocabulary output, and `draftRows` has no subset option.

A gathered/compact head for proposals only can save draft-head traffic; keep target verification full-vocabulary. For sampled speculation, the actual proposal distribution must be normalized over its support and treated as zero outside, including residual sampling. Do not use token ID as a universal frequency ordering. Choose a measured multilingual/code workload or explicit subset policy, preserve special IDs, and count acceptance lost against head work saved. Extra packed-head storage and load-time gathering must be charged; a smaller draft vocabulary is not automatically a whole-round win. I would move MTP preparation onto the device before judging this lever.

## Recommended order

- Prefill: stateless KV-sharing tail pruning first.
- Speculation: device MTP preparation, then bounded device rollback checkpoints.
- Serving: admission-time prefix recheck, then in-flight prefix joining.
- Small kernel change: norm-plus-gate epilogue.
- Disk-bound mixtures: per-page prioritized reads with leases.
- Tuning: row-width-specific GEMM decisions.

No throughput estimates are presented as measurements. All implementations must remain generated, relocatable and budgeted; no new architecture or quantization format is needed for these core ideas. The underlying research used source inspection only; no implementation or benchmark was performed.

## NVIDIA Triton Inference Server and TensorRT-LLM: work before a request

**Triton here means NVIDIA Triton Inference Server, not the Triton kernel language.** The distinction matters: the server chiefly searches deployment and scheduling settings; TensorRT-LLM supplies LLM graph transforms, custom operations and a runtime. Neither implies that jitllm should ship a fixed, compiled engine. These are source-derived proposals, not measured jitllm improvements.

### Three times at which jitllm can do work

1. **Conversion, without knowing the eventual device.** Canonicalize the supported model graph; record tensor shapes, quantization, aliases, state/KV effects, exact consumers and legal fusion boundaries. Compute row-demand/liveness information for prefill. Fold truly constant model expressions or repack weights when the container representation is portable and the numerical contract is verified. jitllm already performs some model-specific folds (`convert/hunyuan.go`, `convert/gemma3nv.go`), fused-tensor splitting and expert-page layout; this is a generalization to *proven* patterns, not a claim these tasks are absent. A possible artifact is a compact graph/legality plan attached to or derivable from the container. It must carry no precompiled kernel.
2. **Device preparation, before admitting requests.** Inspect the actual CPU/GPU, driver, model format, memory budget and representative row widths. Emit a bounded set of legal candidate kernels, reject candidates that exceed register/shared-memory/code-size or scratch limits, check values, and time the *whole recipe* including preparation and reductions. Cache the winning recipe and evidence for that exact scope. The user pays this cost at load/preparation; `cmd/jitllm/speed.go:483` already separates ready-to-first-token latency from load work and checks that compilation/tuning did not leak across the ready mark.
3. **Serving, as conditions change.** Choose among qualified plans using actual batch width, context length, page residency, router choices and active device. Placement, faults and selected experts are runtime facts. A moved block uses the destination device's choice. A search profile can set bounds or initial policies, while existing live adaptation handles drift.

**Legality boundary.** A layer's next normalization consumes a completed residual reduction; graph planning cannot claim exact same-token cross-layer computation before that value exists. It can schedule ready independent branches, remove dead rows, fuse legal producer/consumer regions and prefetch known weights. Any candidate changing reduction order or precision needs numerical gates across positions, devices and relocation. All generated arithmetic stays on the runtime JIT path, and plans remain usable when pages fault or blocks move.

### What Kog's monokernel changes in the experiment

The term now names two different execution scopes. [vLLM's DeepSeek-V4.1 AMD `--monokernel` path](https://docs.vllm.ai/en/latest/api/vllm/models/deepseek_v41/amd/mono_decode/) composes an eligible layer into two persistent FlyDSL launches and performs its TP reductions inside them. It remains a sequence of layer executions on each decode step, with guarded fallback for unsupported conditions. CUDA Graph replay can reduce host dispatch overhead for those launches, but the graph still contains separate device kernels and each new token requires another decode step. Kog's [whole-sequence design](https://blog.kog.ai/building-a-single-kernel-latency-optimized-llm-inference-engine-on-amd-mi300x-gpus/) keeps each GPU's program running through layers, the LM head, sampling and later tokens. Kog therefore addresses the per-token return to the host as well as intra-layer launch boundaries. The supplied Kog comparison graphic describes that scope distinction; vLLM's documentation supplies the concrete two-launch and fallback conditions.

Kog's [MI300X account](https://blog.kog.ai/building-a-single-kernel-latency-optimized-llm-inference-engine-on-amd-mi300x-gpus/) describes one persistent GPU program that executes prefill, the repeated decode layers, the LM head and sampling across the token sequence. Work is mapped to a fixed set of compute units. Kog reports early weight loads across attention and synchronization, QKV weights repacked offline into the order consumed by those units, and handoffs that poll published data with device-scope coherence. It also describes duplicating some reductions and buffers to avoid expensive cross-chiplet communication. Those are separately testable mechanisms; a single launch is not itself evidence of a win.

The reported speed depends on the whole system: eight GPUs, a small model trained with delayed tensor parallelism, hand-tuned hardware mapping and a batch-one workload. Delayed tensor parallelism changes the model's dependency graph; it cannot be applied to an arbitrary pretrained checkpoint by scheduling alone. Kog says the implementation is hand-crafted and highlights nonlocal register, buffer and synchronization interactions. That is a real cost for jitllm's goal of adding models and optimization techniques cheaply. Its current public material is an implementation description, not an available monokernel codebase or a generic model compiler.

jitllm has already tested the nearer control **inside jitllm**: the same model and generated operations run through its ordinary per-operation path or through an optional generated persistent decode-block path. On Llama-3.2-1B Q4_K_M on a V100, the persistent path was bit-identical but ran at 0.89× the ordinary path in the paired in-process trial. In a separate `speed` run with graph replay, the ordinary path read about 518 tok/s and the persistent path about 493–496 tok/s. The optional dependency-counter form read 0.82–0.86× the ordinary graph-replayed path across the three tested V100 models. Both persistent forms were left off by default ([measurements](../engineering-history/gpu-kernels.md#a-persistent-decode-block-composed-bit-identical-and-slower)). These are comparisons between jitllm execution variants, not jitllm-versus-another-engine results. They do not change the published cross-engine scoreboard.

The ordinary block is mostly a chain whose next matvec or reduction needs a completed vector. The persistent variants retained nearly all those phases, exchanging cheap graph kernel boundaries for in-kernel waits and adding constrained occupancy or counter traffic. Kog's claimed advantage includes continuous weight streaming, hardware-specific memory scope, offline layout and an on-device token loop; the earlier jitllm trials did not implement that combined design. A new experiment needs to remove measured waiting or traffic and compare against jitllm's current graph-replayed path, rather than a launch-by-launch control alone.

For jitllm, first profile the actual decode critical path on a target where launch or interstage idle time is material. Trial a **bounded generated region** that prefetches a later weight tile during useful work or a necessary wait, with the current captured execution as control. Record bytes moved, overlap, achieved bandwidth, waits, registers/spills, occupancy, code size and whole-token time. Only enlarge the region when it removes measured waiting or traffic. A full device-resident token loop would also need generated sampling, session control and safe block/token points where pages and recurrent/KV state can relocate; keep those as explicit graph/plan effects. The converter can offer portable layout alternatives, while a hardware-qualified JIT chooses an actual layout and schedule. The optimizer should discover eligible graph regions and effects, not recognize Laneformer by name.

Kog's sentinel polling is a hardware-specific synchronization example, not a portable recipe: valid model data can contain NaN, reused buffers need a new epoch or reset, and acquire/release behavior depends on the backend. Its offline RMSNorm-scale folding and interleaved QKV packing are candidate representations only where they preserve the model's numeric contract, quant format and independent page access. The first question is whether their measured savings exceed conversion cost, extra storage and any loss of paging or relocation flexibility.

### Interpreting Kog's headline speedups

At the time of review, [the homepage](https://www.kog.ai/) currently advertises 30× and compares 3,000 output tok/s with approximately 100 tok/s for ChatGPT. Its separate same-model/same-hardware proof section claims up to 3.5×. These have different denominators; neither establishes a universal 10× engine improvement. The linked [Kog-authored AMD article](https://www.amd.com/en/blogs/2025/kog-reaches-3-5x-breakthrough-inference-speed-on-amd-instinct-mi.html) uses batch one, TP eight, 100-token prompts and 4,096 generated tokens, ten warmups and one benchmark iteration; its baseline versions include vLLM 0.8.3 and TensorRT-LLM 0.20.0rc0. This is vendor-reported historical evidence, not a current paired jitllm comparison.

The [3,000 tok/s preview](https://blog.kog.ai/real-time-llm-inference-on-standard-gpus-3-000-tokens-s-per-request/) uses Laneformer 2B on eight MI300X GPUs, FP16, batch one, without speculative decoding. [DTP](https://blog.kog.ai/delayed-tensor-parallelism-for-faster-transformer-inference/) changes the model so remote contributions can arrive after further local computation; training uses that graph. For existing checkpoints, weight prefetch can overlap communication without that architecture change, but dependent activation computation still waits.

The transferable hypothesis is to combine bandwidth across devices while removing exposed communication and gaps in weight streaming. Persistent execution, generated low-latency collectives, topology-aware handoffs and bounded prefetch are separate candidates. There is no public ablation in these sources assigning the full headline multiplier to monokernel alone. For fixed work/traffic on fixed hardware, a tenfold improvement requires the starting execution to use at most a tenth of its attainable throughput; measure that headroom before interpreting the headline as a jitllm target.

### Joint fusion and partitioning: vertical chains, horizontal slices

The proposed transformation is worth exploring: select a region spanning sequential operations, derive compatible partitions across its producers and consumers, then generate parallel slices that each execute a vertical chain. Fusion and partitioning must be chosen jointly. Removing operation boundaries without changing their dependency structure was insufficient in the earlier persistent-block experiment; a partition can expose earlier useful consumer work.

**Concrete gated-MLP example.** For a completed input vector `x`, write

```text
y = Wdown * (SiLU(Wgate * x) ⊙ (Wup * x))
```

Partition the intermediate channels into disjoint sets `I_i`. Each slice independently computes:

```text
g_i = Wgate[I_i, :] * x
u_i = Wup[I_i, :] * x
a_i = SiLU(g_i) ⊙ u_i
p_i = Wdown[:, I_i] * a_i
y   = sum_i p_i
```

Thus each slice crosses three sequential stages, and its down-projection contribution can begin before other slices finish their gate/up projections. Every gate/up dot product must complete before its SiLU/product. Applying SiLU to partial dot products would be a different function. The final sum must complete before a consumer that requires the complete `y`; changed reduction order and removed intermediate rounding require an explicit numerical contract, not a bit-identical claim. Biases and residuals must be placed once at their proper semantic point.

The partition algebra has an implemented precedent in [Megatron-LM's column/row partitioned MLP](https://arxiv.org/html/1909.08053v4), with [public Python/PyTorch code](https://github.com/NVIDIA/Megatron-LM). That precedent establishes the decomposition, not a single-GPU fused-kernel speedup. [Mirage](https://www.usenix.org/conference/osdi25/presentation/wu-mengdi) provides a compiler precedent for jointly exploring algebra and schedules at kernel, threadblock and thread levels. The jitllm opportunity is to derive legal slices from graph semantics and emit a profitable schedule for the actual device, quantization and residency, without introducing model-name branches.

**Where this extends, and where it stops:**

| Region or axis | Legal opportunity | Remaining dependency or cost |
|---|---|---|
| MLP hidden channels | Independent projection/activation/partial-down chains, followed by a sum. | Each slice reads the completed input. Partial-output accumulation, register pressure and repeated input reads can exceed the intermediate traffic saved. |
| Attention heads into output projection | Completed head outputs can contribute to corresponding output-projection column ranges. | Each head still obeys its attention/KV dependencies; GQA shares KV, and final output channels sum contributions from heads. |
| Consecutive transformer blocks | Pipeline eligible tiles, prefetch future weights, fuse residual/norm consumers where legal. | Dense mixing couples slices again. RMSNorm needs the completed residual's sum of squares; normalization parameters alone do not remove that reduction. No general independent vertical stripe through every block follows from fusion. |
| Prefill token rows | MLP row tiles are independent and can use a different partition from decode. | Attention couples token rows according to its mask; causal readiness and KV writes constrain overlap across blocks. |
| Several GPUs | Place channel slices on devices and reduce their partial outputs. | Communication, residency and synchronization must be priced; this is distinct from distributing slices among one GPU's threadblocks. |

Adjacent purely linear operators sometimes admit matrix composition, but dimensions, offline work, storage expansion, quantization and rounding can make that representation worse. Nonlinear operations generally prevent moving a sum through them. Whole-block independence would require a proof for the actual graph, not merely a persistent launch.

**Fit with the current composer.** [The dependency-block design](dep-block.md) already identifies that split-K narrows producer spans while ordinary output-row matvec tiling reads the whole input. It also lists retaining intermediates on chip as unfinished work. A hidden-channel MLP partition connects these two observations: align producer output tiles with consumer reduction tiles and search the resulting whole recipe. A persistent worker program is one possible lowering; several generated kernels under graph replay are another. The transformation should remain available whichever execution form wins.

**First experiment:** one generated gated-MLP region, comparing the strongest existing recipe plus graph replay against a few jointly chosen hidden/output tile sizes and accumulation schemes. Avoid assuming that a whole `p_i` fits in registers: output tiling may require staging `a_i`, recomputing it, or communicating between workers. Count those costs explicitly. Evaluate decode and representative prefill widths separately; measure whole-token/request time and cold JIT/tuning cost alongside intermediate/partial-buffer traffic, duplicate reads, spills, occupancy and synchronization. Use isolated tuner state and the existing numerical gates. This is a proposed experiment, with no jitllm speedup measured yet.

Conversion can record legal partition axes and portable weight-layout alternatives. The JIT picks the actual tile/schedule and emits every compute kernel. Keep the first region within a relocatable block, lease its pages only for bounded execution, preallocate scratch, and retain a generated alternative for constrained residency. A later cross-block region needs explicit safe points and invalidation when any participating block moves. This preserves paging and relocation while testing the mechanism before committing to a whole-generation monokernel.

### Conversion-time compression and where to decompress

Compressing immutable weights once during conversion can reduce repeated transfer work without changing stored weight values. It need not add CPU work: a generated GPU decoder can reconstruct values as the consuming matvec/GEMM needs them. Distinguish lossless encoding of the existing representation from quantization, which changes values. Bit-exact weight recovery alone does not prove identical inference if the consuming kernel changes accumulation or rounding.

| Representation lifetime | Bytes potentially saved | Runtime cost and scope |
|---|---|---|
| Compressed file; expand into host page | Disk reads and storage. | Host decoding, scratch and full expanded RAM/PCIe traffic. Useful for cold load or disk paging; no resident GPU decode bandwidth saving. |
| Transfer compressed pages; expand into GPU memory | Disk and PCIe/link traffic. | Device decoder plus expanded writes and storage; can pay once per residency period. |
| Keep pages compressed; expand tiles inside the generated consumer | Disk, PCIe, VRAM capacity and weight reads from GPU memory. | Decoder executes on every consumption; register/ALU pressure, indexing and loss of occupancy must cost less than saved traffic. |

The same last principle applies on CPU: decode a small tile near its arithmetic consumer instead of expanding the entire model into RAM. The format should expose independently decodable pages and tiles, bounded scratch and offsets, avoiding serial decode through preceding experts. Codebooks, exceptions, offsets and alignment padding count toward actual bytes transferred. Preserve direct-I/O alignment and separate physical compressed lengths from logical expanded page sizes.

**Implemented leads.** [ZipServ's C++/CUDA artifact](https://github.com/HPMLL/ZipServ_ASPLOS26) uses BF16 exponent bitmap encoding and fused decompression/GEMM; it reports up to 30% size reduction and explicitly targets GDDR GPUs, with benefits varying on HBM systems. [DFloat11](https://arxiv.org/abs/2504.11651) studies entropy-coded BF16 with custom GPU decompression. [Cloudflare's Unweight kernels](https://github.com/cloudflareresearch/unweight-kernels) provide CUDA implementations for BF16 MLP compression on Hopper. These establish available mechanisms, not a measured gain for jitllm's Q4/K-quant pages. Their deployed kernels cannot be imported as the jitllm compute path; the selected decoding algorithm must have generated lowerings.

For a serial transfer/decode stage, let `S` be original bytes, `r` compressed/original size including metadata, `B` link bandwidth and `D` decoder throughput measured in expanded bytes/s. Ignoring fixed overhead, compression pays when `r*S/B + S/D < S/B`, or `D > B/(1-r)`. For example, at `r=0.7` and `B=25 GB/s`, decoding must exceed roughly `83 GB/s` in this simplified model. Overlap changes the sum toward a pipeline maximum, but contention and extra writes must still be measured. HBM consumption demands a much faster decoder than disk or PCIe transfer; one codec need not win at every tier.

**First filter:** sample real dense, expert and head pages across existing precisions; measure lossless ratio and decode cost, including outlier tiles and metadata. Do not assume Q4 streams have the same redundancy as BF16 exponents. Then compare page expansion versus fused consumption on the bottleneck tier, with uncompressed pages as a per-page option. Account for compressed plus expanded peak memory and scratch. A smaller representation that eliminates recurring page faults can gain much more than its percentage byte reduction, so include a near-capacity workload. Converter-time encoding can be expensive; warm runtime decoding must remain generated, preallocated, pageable and relocatable. This is research planning, not authorization to add a format or a new measured performance claim.

**Preferred experiment for models that evict pages (user direction).** The scope is eviction behavior, regardless of model size or the machine's installed memory. A small model can evict under a user-assigned budget; relocation can change residency and cause evictions. Compress eligible immutable weight pages ahead of time during conversion, record their encoding in the model container, and retain that representation through storage, residency and transfers; reconstruct only bounded tiles inside generated compute kernels. Avoid requiring a full expanded layer or model as a staging allocation. Whenever pages must be evicted and faulted back in, continue paging compressed pages normally. Test host and device eviction paths separately: saving bytes across disk and across PCIe has different break-even costs.

The proposed page descriptor records codec/version, logical weight format, compressed byte length, expanded logical extent, tile offsets and any codebook/exception metadata. Residency accounting charges actual physical allocations, including alignment, metadata and scratch. Relocation preserves logical weights and carries the decoding metadata; every participating backend needs a generated decoder before this representation counts as supported. Warm decoding uses preallocated tile scratch and no Go arithmetic. The converter leaves poorly compressing pages in the existing representation and records that choice explicitly.

**Ahead-of-time compression, load-time selection, runtime-generated kernels (revised user direction).** Conversion creates independently indexed compressed pages and records codec/layout versions, original weight formats and decoding metadata in the container. Loading reads those descriptors, so the engine knows which blocks require decompression instructions before execution. Mixed compressed/plain pages must be described explicitly; a model-wide boolean is insufficient if their encodings differ. The JIT emits consuming recipes with fused decoding for the actual device. Compression happens ahead of time; executable kernels remain generated at runtime.

Evictions and budget changes use the existing compressed representation without triggering compression or re-emission merely because a page faults. Relocation can require a new device-specific generated variant, with the same logical weights and decoding metadata. Bind executable variants and page representations consistently, wait for outstanding readers before replacing bindings, and invalidate affected captures when addresses or layouts change. Key variants by codec/layout version, original quantization, shape and target device, with pointers rebound separately. Account for metadata, alignment and bounded tile scratch in residency budgets, and include initial emission or relocation preparation in the corresponding latency measurements. No full expanded layer is required by this path. Every participating backend needs a generated decoder before the representation counts as supported.

Compare ordinary paging with compressed paging plus fused consumption under the same assigned memory budgets and relocation trace, including scratch. Cover a resident control, cases where compression prevents evictions, and cases where both representations still evict. Include a small model with a deliberately restricted budget, budget changes during a sequence, and relocation that causes evictions. Measure cold TTFT, warm tok/s, actual disk/PCIe/HBM bytes, faults, peak residency and decoder resource cost. Distinguish gains from avoided evictions from gains due to smaller transfers when evictions persist. No gain is assumed until actual packed-weight compression and whole-request timing are measured. This prioritizes the experiment without selecting a new production format yet.

### A measured caution for fine-grained placement

[ATSInfer](https://arxiv.org/abs/2607.10183) proposes tensor-level static placement with load-aware dynamic transfers. A [public C++ llama.cpp-family implementation and audit](https://github.com/lordnyx0/ik_llama-atsinfer) reports its placement solver **lost on its measured decode case** because it split gate/up/down decisions and broke a fused MoE path; its transfer promotion could cost more PCIe time than it saved. This does not refute the paper's other hardware, but it is a concrete constraint for jitllm: a placement unit must carry the composer recipe and its consumers, not merely one tensor's bytes and isolated compute time. jitllm's existing block-level relocation remains the control arm for any finer plan.

**Order after screening:** (1) collect the layered-prefill traffic trace, because it tests a new scheduling axis without changing the model; (2) measure lossless compression on *actual* JLM pages as a cheap offline filter; (3) audit HELM's model against existing seam measurements; (4) inspect KV transfer compression only where transfer time is visible. None is a rate claim or a request to add a quantization format now.

## Toward a model-graph JIT and an optimizing converter

This proposes the graph machinery needed to compile previously unseen model combinations and reduce family-specific execution code; it does not change the architecture-admission policy or any gate in `AGENTS.md`.

### What is currently hardcoded, and what can become generic

`convert/config.go` maps GGUF architecture strings through `archOf`; `convert/safetensors.go` maps Hugging Face class names through `hfArchTable`. Those tables select class defaults, tensor mappings, graph conventions and fixups. The JLM `Config` (`format/jlm/config.go`) stores an architecture code and many feature fields, not a complete executable graph. `engine/nn/device.go`'s `LayerPlan` carries a growing set of graph-shape flags. `engine/model/forward.go` and device layer execution then reconstruct the block from those flags and family checks. `jit/ir` describes **individual kernels**, below the level where an optimizer could reason about two projections, a KV update and the next block together. The composer adds recipe selection at kernel sites; it does not yet supply a model graph.

The near-term milestone is an *authorized* new model whose computation uses existing operations, added through a small converter mapping or graph manifest and **no new family branch in the host or device executors**. A generic importer can remove the mapping when a trustworthy executable graph exists, but that is an optional improvement rather than a condition for useful performance. A genuinely new operation, state transition or input-preprocessing rule still requires reusable generic support. A weight archive and tensor shapes alone do not determine whether a model normalizes q before or after rotary, which router function it uses, or how it updates recurrent state. Guessing those semantics would produce plausible but wrong text. `hfArchOf` already treats the source class as authoritative; `model_type` is insufficient when similarly named classes have different graphs.

### The missing representation

Add a versioned, validated **model graph** above the current kernel IR. It should describe tensor values, symbolic dimensions, constant parameters and stateful effects. A small illustrative block is:

```text
v0 = rms_norm(input, attn_norm, eps)
q  = matmul(v0, wq)
k  = matmul(v0, wk)
v  = matmul(v0, wv)
q1 = rope(q, position, layout=interleaved, sections=...)
k1 = rope(k, position, layout=interleaved, sections=...)
a, kv1 = causal_attention(q1, k1, v, kv0, window=...)
v1 = add(input, matmul(a, wo))
f  = rms_norm(v1, ffn_norm, eps)
g  = silu(matmul(f, wgate))
u  = matmul(f, wup)
output = add(v1, matmul(mul(g, u), wdown))
```

This is a notation example for one block, not a universal attention formula. Common subexpressions are explicit graph values. The graph needs exact contracts for rotary coordinate layout, norm placement, causal/window/chunk masks, attention sinks and softcaps, quantized projection semantics, router scoring/top-k/tie handling/combination order, and scan/recurrent updates. Higher-level patterns such as attention and MoE can remain recognizable during optimization; their semantics must still be defined through typed inputs, outputs and effects. A single opaque `run_layer(arch=...)` node would preserve today's problem.

KV pages, recurrent state, position inputs, expert selections, page leases and transfers belong in the dependency model. Represent reads and writes with explicit state versions or effect tokens, plus aliasing and liveness. Then a scheduler can prove when an activation tile is ready, which update may cross a device boundary, and when a page can be evicted. Dynamic routing values should select already compiled paths at run time; recompiling for each expert combination would explode the cache and cold latency. Shape ranges and guards must distinguish decode, prompt rows, context lengths and ragged batches.

### Division of labor

| Stage | What it should decide | What it should preserve |
|---|---|---|
| Trusted converter frontend | Read a reference class or a declarative graph manifest; resolve class-specific defaults; map and validate every weight and buffer; reject ambiguous or unsupported semantics. An export such as [`torch.export`](https://docs.pytorch.org/docs/stable/export.html) is one possible graph source, but its trace and shape assumptions require checking, and arbitrary Python/custom ops are not automatically supported. | A checked graph and all inputs needed to reproduce the source computation, including tokenizer and multimodal preprocessing contracts. |
| Offline, target-independent optimizer | Canonicalize layouts/names; infer shapes and liveness; fold true constants; perform algebraic rewrites only with an explicit numeric contract; identify potential fusion, independent branches, page units and stateless tails. Store a baseline graph alongside optimized variants and their legality conditions. | No device-specific executable kernel in the container; portable pages and enough metadata for relocation and future backends. |
| Device preparation JIT | Inspect the actual CPU/GPU and memory budget; partition the graph into regions; choose composer recipes, fusion cuts, tiles, reduction form, dequantization placement and scheduling; emit each kernel through jitllm's existing generated-code pipeline; measure a bounded candidate set and cache results under device/shape/format keys. | A BASIC generated implementation for every supported op if a faster recipe fails; the five project principles. |
| Runtime plan | Execute prepared regions with changing token, page and expert addresses; fault/evict/relocate state and weights; replan or recompile as placement changes. | Zero warm-token Go allocations and no Go arithmetic on the token path. |

The offline optimizer can change a **stored representation** when it is lossless and format-compatible; hardware-specific packing can also happen during device preparation. Lossy quantization and approximate rewrites are separate model-changing choices. Even algebraically exact reassociation can change floating-point rounding and top-k decisions, so each rewrite needs an allowed error policy and values-level tests, especially around router ties. The converter must not infer a missing Hugging Face class default from a similar model. Tokenizer, chat template and vision preprocessing are separate input programs with their own verified representation; a tensor graph cannot infer them from weights.

### How to migrate without a second hand-maintained executor

1. **Specify the IR and verifier on existing models.** Emit the graph from the current trusted converter for one plain dense block, then one with q/k norm, post-norm or sliding attention. Serialize op versions, symbolic shapes, weight bindings, state effects and numeric semantics. Validate the graph before accepting a container; unknown ops fail clearly. This can start with existing architecture codes and admission rules intact.
2. **Lower those graphs through existing generated kernels.** Begin with a prepared execution plan that invokes existing host/device JIT kernels. This removes family graph reconstruction before attempting ambitious fusion. The host and device, decode and batch paths should consume the same semantic graph, with backend-specific schedules.
3. **Demonstrate one useful optimization on that slice.** Feed an eligible region to the composer and bounded autotuner. Discover an existing fusion by graph pattern, compare complete recipes against the unfused prepared graph and the current executor, and include CUDA Graph or equivalent launch controls. Record whole-request performance and preparation costs before expanding the graph machinery.
4. **Reuse the machinery on another approved model.** Bind a different combination of the supported operations through a compact converter description. Show that the same pattern and recipe apply without another family runtime path, then use profiling to choose the next targeted optimization. These steps correspond to Slices A–D below.
5. **Broaden coverage as workloads require it.** MoE tests dynamic routing and ordered combination; MLA and recurrence test explicit state updates; multimodal models test non-text inputs and positions. Add the needed operations and effects incrementally. Cross-layer overlap, tile streaming and page-aware scheduling can be trialed as soon as their particular dependencies and migration boundaries are expressible. Broader architecture coverage is not a prerequisite for optimizing an already covered region.

An intermediate milestone is **one new, explicitly approved model variant using existing graph operations**, converted with only a small frontend mapping or manifest and validated on all required tiers, without edits to `engine/model/forward.go`, `engine/nn/device.go`'s family switches or the device layer executor. A new op is a separate compiler/backend task. Gates include independent reference values from randomized weights **and buffers**, nonzero positions, prefill/decode, paged and relocated state, partial CPU/device placement, and zero warm allocations. Performance needs same-pass whole-token baselines and preparation-time/memory accounting under `AGENTS.md`; a smaller executor alone is not a performance result.

This direction resembles [TVM Relax's graph IR combined with TensorIR](https://tvm.apache.org/docs/deep_dive/relax/index.html) and [IREE Stream's explicit resources, affinity and timepoints](https://iree.dev/reference/mlir-dialects/Stream/). They are design precedents, not dependencies or proof that they cover jitllm's paging and relocation contracts. [MLC LLM's architecture guide](https://llm.mlc.ai/docs/compilation/define_new_models.html) explicitly distinguishes a new weight variant from new inference logic: even a compiler needs a source for the model's semantics.

### The three representations, with a block boundary that survives optimization

The proposed pipeline has three distinct levels. Their interfaces matter more than their package names:

```text
GGUF / safetensors + trusted class adapter or verified graph manifest
                  |
                  v
       semantic model graph (portable, versioned)
       block templates + per-block parameters + state effects
                  |
        offline validation and portable rewrites
                  |
                  v
       JLM graph + weight bindings + pageable storage
                  |
        inspect real device, memory budget and current placement
                  |
                  v
       execution plan (regions, leases, transfers, shape guards)
                  |
        composer chooses generated recipe per region
                  |
                  v
       existing CPU emitter / GPU kernel IR -> actual machine kernels
```

The **semantic graph** answers *what values and state updates constitute the model*. The **execution plan** answers *where and when those operations run with today's placement and row shape*. The current kernel IR answers *how one selected computation runs on this device*. Keeping those questions separate allows offline work without shipping precompiled code, and runtime tuning without changing the model's meaning.

At graph level, a model can have functions such as `embed`, `block`, `final_head`, `vision_tower`, `projector` and `decision` as applicable. A repeated block is a template instantiated with that layer's weights and parameters. Layer kinds become different graph instances or templates, not `if arch == ...` in the executor. Proven equivalent source classes can share a canonical graph; the source class and architecture code remain provenance and admission metadata. A normalized graph fingerprint helps identify repeated structures and reuse *candidate discovery*, but it is not evidence that two checkpoints implement the same function or that one device's timing verdict applies to another.

**Block boundaries remain materialization and migration points.** RULE 8a requires each block to stay independently orchestrable; paging and relocation must work even if a fast plan temporarily fuses blocks that share a device. A cross-block recipe is conditional on their current co-placement and state ownership. At the next safe token boundary, the planner can discard that recipe, materialize the residual and use individual block plans after a move. The semantic graph cannot require an entire fused multi-block region to stay resident. Existing CUDA graph capture and host region fusion remain execution-plan choices, not replacements for these boundaries.

### A graph type system that can reject wrong models early

Each value needs a dtype, shape with bounded symbolic dimensions, layout, quantization interpretation and ownership. Each weight reference needs a container role, byte range, source name/provenance and a checked shape. An operation has an **op version** and explicit semantics: for example `rms_norm` states epsilon placement and accumulator precision; `rope` states pair layout, coordinates and base/scaling; `topk` states tie/order behavior; `quant_matmul` states dequantization and accumulation. `add` alone cannot specify whether a router's selected experts are accumulated into a separate buffer or directly into the residual. The numerical contract must name the sequence of additions when it affects decisions.

An illustrative *stateful* fragment is:

```text
%n          = rms_norm(%residual, %norm_weight, eps=...)
%q, %k, %v = projections(%n, %wq, %wk, %wv)
%qr         = rope(%q, position, layout=..., sections=...)
%kr         = rope(%k, position, layout=..., sections=...)
%kv_next    = kv_append(%kv_prev, %kr, %v, sequence_slot, position)
%a          = attend(%qr, %kv_next, position, mask=causal, window=...)
%next       = add(%residual, project(%a, %wo))
```

`%kv_prev` and `%kv_next` are *logical state versions*. The plan gives them physical pages, leases, transfers and completion events. A later attention read of `%kv_next` cannot move ahead of its append. A weight page is read-only but must be resident and pinned while a kernel uses it; a KV page or recurrent state also has a writer, an owner and an eviction/relocation rule. For a prompt chunk, the graph must express that all rows' K/V writes become visible before an attention row reads earlier rows in that same sequence. `forwardRows` documents exactly this ordering today. A compiler without state effects can easily produce a faster, wrong schedule.

The verifier can check before allocation or emission: every referenced weight exists with the expected size/type; each symbolic dimension is in range; every state read has a valid predecessor; aliases and mutable writes are ordered; every graph output is produced; all op versions have lowerings on the required tiers; and requested scratch, pages and code size have bounded estimates. This is also the place to refuse malformed or unsupported graph containers without sizing memory from unchecked header counts. A generic runtime should accept a **small validated op language**, not executable Python or an arbitrary source-level callback inside a model file.

The op vocabulary needs several levels of meaning, rather than one enormous `attention` or `moe` switch:

| Kind | Examples | Why it is explicit |
|---|---|---|
| Pure tensor operations | matmul with a stated quant/dequant contract, add, multiply, activation, norm, reshape/view, position transform, reduction | Their dataflow supports liveness, CSE and fusion legality. |
| Structured patterns | causal/sliding attention, grouped expert projection and combine, convolution, bounded scan/recurrent update | The compiler can recognize a useful fast implementation without hiding the operation order or inventing one family-specific primitive per model. |
| Dynamic choices | top-k, gather, expert IDs, mask/window selection, ragged row-to-sequence mapping | Values depend on this request. Shape guards can specialize known dimensions; the chosen experts remain runtime data. |
| Persistent effects | KV append/read/trim, recurrent-state version/commit, page lease, transfer and completion | They prevent illegal movement across state writes and allow a plan to explain residency and rollback. |

For example, **Qwen3 q/k norm** is two norm nodes placed before rotary; **Gemma2 post-norm and attention softcap** are extra nodes at their actual positions; **DeepSeek MLA** changes the cache value type and attention subgraph; **a MoE router** is scoring, selection, gather, expert work and an explicitly ordered combine. These are graph structures and op parameters. If the only way to express one is `if arch == Qwen3` inside a kernel or executor, the vocabulary is still missing a semantic distinction. Conversely, a generic graph of scalar adds and multiplies alone would hide useful attention and scan patterns from the composer, so pattern recognition and typed structured regions are part of the design.

A composer's candidate can be described by `(matched graph region, shape/format guards, required effects and resource bounds, generated lowering, numerical contract)`. The matcher might find `norm -> gate/up -> activation -> product` in any authorized model with those semantics. Its reference recipe can launch existing BASIC generated kernels; alternative recipes can use the current `Gate2`, `gate2in` or future emitters where their guards hold. The tuner times the *whole matched region* on the target. That interface also makes backend gaps visible: a candidate unsupported by Metal is simply absent there, while the graph's BASIC lowering still runs on Metal as RULE 8 requires.

### Where semantics come from

There are three realistic frontends, in decreasing order of what source knowledge they can provide:

| Source | What the converter can know | Remaining work |
|---|---|---|
| A reference implementation plus an exportable inference path | It can capture a forward graph and inspect parameters and buffers. [TensorRT-LLM AutoDeploy's export stage](https://nvidia.github.io/TensorRT-LLM/features/auto_deploy/transforms/export.html) is a concrete precedent. | `torch.export` may need dynamic-shape annotations or code changes and cannot trace every Python feature or data-dependent branch ([PyTorch limitations](https://docs.pytorch.org/docs/stable/export.html#limitations-of-torch-export)). An ordinary training-style `forward` does not necessarily specify jitllm's paged decode, KV ownership or recurrent rollback; these must be supplied and verified. |
| A declarative, versioned graph manifest shipped or curated with the checkpoint | It can specify operations, parameters, state and input contracts without executing source model code at inference. | The manifest still needs provenance and comparison against the source implementation; a wrong manifest is a wrong model. |
| GGUF or safetensors weights plus config alone | It provides names, dimensions, values and some declared hyperparameters. | Many semantics are absent or ambiguous. Keep the existing verified architecture/class adapter as the trusted frontend and make its output the canonical graph. Unknown names or contradictory defaults remain refusals. |

This is how hardcoding moves out of the hot path **without pretending model semantics can be inferred from tensor shape**. Initially, `archOf`, `hfArchTable` and the class-specific converter functions remain: they resolve source quirks into one graph language. Over time, a manifest or reliable export can replace an adapter for a specific approved class. The project's architecture list and user decision in RULE 7 remain in force until explicitly changed. Tokenization, chat templating and image/audio preprocessing need their own verified input-program contracts; a tensor graph covers the network computation only.

### Offline passes that have a concrete legality story

| Pass | Opportunity | Legality and cost boundary |
|---|---|---|
| Canonicalize source tensors | Normalize names, transpose/view layouts, split fused qkv or gate/up, bind tied weights, and eliminate copies that only change naming. | Validate every source tensor and buffer, row order and byte interpretation. Some transformations are views; a physical repack changes page bytes and must preserve random access and exact stored values. |
| Infer shapes, uses and row demand | Determine which prompt rows must reach each operator, which outputs feed logits, and which rows must still write KV or recurrent state. | A stateless tail may drop unused intermediate rows. Attention or recurrence cannot drop a row whose state is needed later. This is the precise precondition for the stateless-tail idea above. |
| Fold constants and common pure subgraphs | Precompute position-independent constants and share identical pure normalization/projection inputs. | `position`, context window, selected experts, page residency and per-session state are runtime values. Float operation order still matters. CSE never merges stateful calls. |
| Select storage and page units | Group immutable weights by use; keep expert banks independently addressable; record prefetch candidates and exact weight-byte demand per graph region. | The physical format must keep a block pageable and relocatable. A layout that saves launches while forcing all experts into one page can lose badly under a tight budget. Any new quant representation follows the format and oracle gates. |
| Mark fusion and overlap candidates | Discover producer-consumer chains, independent q/k/v or gate/up branches, and regions the composer can implement. | Mark candidates, not mandatory fusions. Extra register pressure, duplicate reads, workgroup barriers, code size, launch cost and paging traffic decide the winner on the target. |
| Algebraic weight folding or reassociation | In restricted cases, absorb a constant affine scale/bias into a following projection or rewrite two projections. | Dequantization, quant block layout, F32 rounding and intermediate dimension can reverse the benefit or change decisions. Require a named numeric contract and independent value tests; do not assume real-number algebra proves model equivalence. |

Offline analysis can produce *facts* and legal alternatives even when it cannot pick the fastest tactic. The device JIT then searches a bounded set using the actual card, row width, weight format, residency state and workload profile. This builds directly on jitllm's current auto-tuners and the composer. It avoids tuning a nonexistent cross-product of every fusion, split and placement: statically reject impossible candidates, rank plausible ones by resource/traffic estimates, then time complete recipes. A cache key needs compiler/op versions, backend and device features, shape range, quant format, relevant layout and memory mode; an entry is evidence for that key, not a portable performance claim. Cache reuse must preserve the five principles: it may reuse decisions, while kernels are still emitted for the device at runtime.

### What this actually unlocks

| Capability | Why the graph is the enabling piece | Earliest credible result |
|---|---|---|
| Fewer family branches and less drift | One graph defines operation order for host, device, single-token and batched execution. The existing [three-transcriptions failure](../engineering-history/model-correctness.md) shows why this matters. | Dense blocks reach identical answers through two prepared plans built from one graph. |
| Model additions through data and adapters | A class with existing operations can bind weights and constants to a graph template. | An approved model variant adds no family branch to `forward.go` or the device layer executor. |
| General composer sites | The producer, consumer and numeric/effect boundaries are data, so recipe enumeration need not be wired to one named FFN or attention family. | One existing `gate2in`-like site is found by pattern and still chooses its measured recipe. |
| Row liveness and exact prompt pruning | The graph exposes whether a row has a later consumer or persistent-state write. | A stateless KV-sharing tail executes only demanded rows and matches logits/state against the existing path. |
| Page-aware placement and prefetch | The scheduler sees a region's precise weight roles, state ownership, activation live range and future use. | A trace predicts page bytes and transfers, then a bounded placement trial tests whether it improves whole-token time. |
| Cross-layer scheduling | It can schedule ready work within or across co-placed blocks while preserving state and migration boundaries. | First demonstrate an actual removed intermediate, launch or wait against the existing graph-captured baseline; tile counters alone already lost on V100 decode. |

The dependency graph also tells us where a hoped-for overlap is **impossible**. A decode matvec row generally reads the full upstream vector; RMSNorm needs a full-row reduction; softmax needs its score reduction. Completing one upstream output tile often does not make a valid next-layer tile ready. Independent branches and asynchronous page reads are the credible early overlap cases. Partial-output propagation is useful only where its narrower dependency and accumulation cost beat the ordinary plan. The [dependency-counter block](dep-block.md) already records the all-to-all versus tile-local distinction and why a scheduling-only decode composition regressed.

### A small proof of value before a general compiler project

**Slice A: semantic graph, same execution.** Emit a versioned graph for two existing dense block variants and the head. Make a plan from it that calls the *existing* generated operations, preallocating addresses and scratch. Keep the current executor as a comparison arm during migration. The graph verifier and format round-trip should detect a missing q/k norm, changed rotary layout, absent KV write and bad tensor binding. This tests whether the IR is expressive before asking it to optimize.

**Slice B: one plan feeds every mode.** Derive host and device, decode and batched plans from the same graph; compare nonzero-position logits and intermediates, random weights and buffers, prompt chunks, partial seams, relocation and paging. Confirm the plan's counters show the intended graph nodes and devices actually executed. A prepared plan must not allocate on a warm step or dispatch arithmetic through Go.

**Slice C: one graph-discovered optimization.** Have the composer identify an existing legal site, offer the existing reference and fused recipes, and tune the whole region. This distinguishes a *real* graph compiler from a new serialization format around today's manual switches. Count launches, moved bytes, register/spill/occupancy costs and preparation time as well as whole-token latency. A clear regression rejects the chosen recipe for that device/shape, not the graph architecture.

**Slice D: prove extension without a family runtime branch.** Convert one newly approved class or variant whose operations are already covered, using a small verified adapter, graph manifest or generic source importer. Run its architecture gates from `AGENTS.md` across every tier, including partial placement, paging, relocation, allocation and a real checkpoint/reference. Record the converter and engine code changed, plus TTFT, tok/s and preparation cost against the existing plan. If its graph needs a new primitive, add that primitive and its BASIC generated lowerings rather than disguising it as an opaque model-family callback.

The first two slices can improve **correctness and maintainability** even if speed is unchanged. The performance hypotheses start at Slice C. The main costs are a versioned container graph, state/effect semantics, backend coverage for each op, validation, cold plan construction and migration of several execution paths. The project should measure those costs explicitly; it should not replace a fast, correct hand-built plan merely because the new representation looks cleaner.

## Work backward from first-token time and generated-token rate

The objective is request performance under the five principles in `AGENTS.md`. A model graph, converter pass or composer feature is useful when it reduces a measured request cost or makes a previously valid plan possible. The graph proposal above is one way to expose the facts a planner needs; it is not itself the target metric.

### Define the objective by lifecycle and workload

These are distinct measurements; collapsing them into one "TTFT" or "tok/s" number makes the wrong plan look attractive:

| Metric | Boundary and cost to account for | Why a different plan may win |
|---|---|---|
| Cold process-to-first-token | Open/container reads, device initialization, placement, uploads, JIT emission, tuning, session setup, prompt processing and response. | An expensive layout conversion or broad tuner can lose before its steady-state kernel repays it. |
| Loaded request TTFT | Queue/admission, tokenization/input preprocessing, session attachment or prefix restore, page faults, prefill, final projection, sampling/readback and response. State whether tokenization and network time are included. | Short prompts expose fixed overhead; long prompts expose prefill compute, KV writes, device seams and page traffic. |
| Single-sequence decode rate | The generated tokens after the first divided by elapsed first-to-last-token time, with context depth and generation length stated. | Resident decode may be weight-bandwidth bound; deep-context attention/KV and over-budget page reads change that. |
| Concurrent output rate and inter-token delay | All generated tokens over wall time, alongside per-request p50/p95 TTFT and inter-token delay. | Larger batches can share weight reads but delay a waiting prompt. Aggregate tok/s alone can reward an unacceptable queue. |

The repository already treats load, model-loaded TTFT and warm prefill as different rows ([current board](../perf/current.md#the-prompt-rows-and-their-boundaries)). Its server TTFT includes send-to-first-text, whereas a `speed` row may exclude tokenization or network time; those boundaries belong beside every result. [NVIDIA Triton Model Analyzer](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/model_analyzer/docs/config.html) likewise exposes TTFT, inter-token latency, output-token throughput and memory as separate objectives or constraints. The relevant workload describes prompt-length distribution, generated lengths, context depths, simultaneous sessions, prefix reuse, model-fit versus over-budget periods, and cold versus warm process frequency. The search should keep a **Pareto set** for TTFT, per-stream rate, aggregate rate, memory and cold preparation rather than declaring a universal winner.

An approximate accounting identity for one request is `completion time = TTFT + sum(inter-token intervals)`; cold process time adds open/attach before request TTFT. For a candidate that adds preparation time but saves `delta` seconds per generated token, the rough break-even is `extra preparation / delta` tokens. A persistent tuning verdict can amortize across processes, but its key must be scoped to the device and workload shape. This arithmetic ranks experiments; it does not replace a whole-request measurement.

### Diagnose before choosing an IR feature

Build a per-request **critical-path ledger** from existing counters and traces. Attribute time to queue/input, host compute, device compute, device submission, host-device transfers, page reads/uploads, KV operations, final projection/readback, and first-use preparation. Attribute bytes to stored weights, KV, activations, disk/page reads and links separately. Count the shape buckets actually executed and the chosen recipe. A DAG planner also needs dependencies and resource occupancy: two independent operations can overlap only if they do not saturate the same memory link, execution units or cache.

The current evidence demonstrates several different limiting resources:

- In the dated V100 70B multi-card decode row, about **41.9 GB of weights/token** at roughly **17 tok/s** implies about **712 GB/s**, 80% of that pass's measured one-card read wall ([board](../perf/current.md#v100-box-big-models-decode-time-to-first-token-vram)). A fusion that only removes a small launch cannot remove most of that cost. Byte traffic, memory efficiency and work sharing across sessions are stronger hypotheses there.
- A 2048-token prompt split over several cards previously ran the cards mostly in turn; pipelining 512-row pieces is already implemented and measured at **1.6–2.2x** on the cited models ([multi-card prompts](../perf/current.md#multi-card-prompts-cold-start-sessions-together-v100)). A new compiler must start from that baseline, then look for remaining compute, seam or liveness costs.
- Qwen3-30B-A3B's dated cold phases fell from **26.0 to 13.9 seconds** after removing duplicate host expert frames and improving upload staging ([same section](../perf/current.md#multi-card-prompts-cold-start-sessions-together-v100)). That gain came from residency and startup work, not a faster matmul.
- Kimi-K3's over-budget run read about **6 GB of pages per generated token** and was dominated by the latency of many expert reads; the source explicitly did not measure a disk bandwidth wall in the same pass ([Kimi-K3 record](../perf/current.md#kimi-k3-278t-from-disk-on-the-v100-box)). Packing or scheduling expert pages matters more there than a register-level matvec change.

These are **dated workload diagnoses**, not transferable speedup estimates or a replacement for RULE 1's same-pass baseline. They illustrate why one generic graph optimization cannot be the first answer to every row.

### Search over complete execution plans

The unit of search should be a *plan for a workload phase*, subject to the model's exact graph and the five principles. It combines choices that interact:

| Choice | Examples | Cost it can move |
|---|---|---|
| Storage/layout | Lossless weight packing, independently addressable experts, page size, precomputed constants and legal views. | Bytes/token, random read amplification, upload time, peak RAM/VRAM, conversion and cold attach. |
| Placement/residency | Block and head location, capacity reserved for KV and experts, page leases, read-ahead for statically known future weights. | Device seams, page faults, transfer wait and resident capacity. |
| Compute recipe | Dequant placement, GEMM/matvec form, split/reduction, fused prologue/epilogue, attention form, graph capture. | Compute time, launch count, intermediate traffic, registers, scratch and code size. |
| Work partition | Prompt chunk width, multi-card pipeline stages, row grouping, batch admission, per-session scheduling. | TTFT, inter-token delay and aggregate output rate, with KV pressure as a constraint. |
| Preparation | Which shapes to emit and tune before ready; how much bounded trial budget to spend per hot site. | Cold time, first-request stalls and later decode savings. |

The converter supplies semantic legality, weight use, possible portable layouts and perhaps several *descriptions* of legal representations. It does not bake a GPU-specific kernel or a universal winning schedule into JLM. The runtime planner inspects hardware, capacity and current placement, constructs feasible plans, and measures a bounded set of complete alternatives. The composer is its compute-recipe component. Existing separate tuners remain useful; the broader planner prices their interactions with page size, scratch, launches and phase-specific row widths. [TVM MetaSchedule](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/meta_schedule.html) is a precedent for workload-weighted tasks, a global trial budget, measured records and a cost model; its per-operator objective is narrower than jitllm's whole-request plan objective.

The semantic graph needs BASIC generated coverage on every required backend. Each optimized candidate needs a valid lowering only on the devices where it is offered; a CUDA-only recipe may compete on CUDA while Metal uses another generated plan. Relocation selects a qualified plan for the destination. For each candidate, the planner checks graph and numeric correctness, backend capabilities, bounded scratch/code and memory, legal state ownership, independently pageable/relocatable blocks, and zero warm-token host allocation. A cheap cost model then **ranks** candidates by bytes, operations, launches, transfer critical path and preparation. Whole-phase or whole-request trials decide the winner. A locally faster kernel can lose after it expands pages, evicts KV, changes the number of transfers or delays the first response. A plan change that causes paging has a discontinuous cost; additive per-kernel timing cannot predict it reliably.

Whole-plan tuning requires an explicit trial lifecycle. Run candidates in dedicated trial sessions with private mutable buffers; weights may be shared read-only. Before each arm, restore the same logical inputs, token positions, KV contents and lengths, recurrent/convolution state, speculative checkpoints and sampling RNG state where applicable. Drain outstanding device work and I/O before restoring or recycling trial storage. Trial outputs never advance a live request. If a stateful region cannot yet be isolated and restored correctly, retain its qualified plan and restrict tuning to regions with a safe trial implementation.

Residency is also part of the experiment. Specify the memory ceiling and the intended starting state of weight, KV, prefix and staging caches. For a warm trial, prepare both arms to the declared warm condition; for a faulting trial, restore the same logical residency and replay the same workload independently. Account for shared caches and concurrent work: a private session alone does not isolate the page cache or GPU. Use an isolated measurement window when resource contention would invalidate the comparison, and report any uncontrolled hardware or OS cache effects. Candidate-induced faults, evictions and transfers remain inside the timed workload. Interleave arms under the project's measurement rules.

Snapshot construction, restoration and trial buffers count toward tuning time and peak memory, even when restoration is outside the steady-state interval being compared. Production-required packing, transfers and setup stay in their applicable metric. Preallocate reusable trial storage and bound the preparation budget. On trial failure, discard its state and keep the incumbent plan. Install a qualified winner at a safe execution boundary, after rebuilding any dependent kernels, buffers or captures; verify that running trials leaves an independent session's continuation unchanged.

### Phase-aware decisions that the same model may need

| Situation | Likely first question | Useful graph/plan fact |
|---|---|---|
| Short, loaded prompt | Where is the fixed request/launch/readback cost? | Exact executed path and shape; the last demanded logit row; whether a fused recipe removes an actual submission. |
| Long prompt or vision input | Which GEMM/attention stage, row padding or cross-card seam is on the critical path? | Row liveness, dependency-safe chunking, activation live range, stage occupancy. The existing multi-card prompt pipeline is the control. |
| Resident single-stream decode | How many bytes must be read per token, and how close is that to the measured wall? | Weight roles and actual packed bytes, KV depth, device-specific recipe cost. Tiny launch savings must be priced against bandwidth and occupancy. |
| Over-budget or routed decode | Which demanded pages missed, and how much time was read, transferred or wasted on a too-large page? | Per-expert/page use, earliest legal prefetch point after routing, pin/evict rules and co-location of recipe consumers. |
| Concurrent serving | Does grouping rows save repeated weight reads without violating TTFT/inter-token targets? | Ragged row mapping, state ownership, KV capacity and phase-specific batching cost. |

The **first plan** can be a quickly prepared, fully generated BASIC plan with all required state and placement support. Further measurement can replace it only when the request/workload's amortization and SLOs justify the trial; this does not imply lazy emission of a missing kernel on the token path. A long-running server and a one-shot CLI can therefore choose different tuning budgets while running the same model graph. Moving a block to another device preserves the semantic graph but invalidates the affected physical plan and its dependent transfers, cross-block recipes and captures. Rebuild that dependency closure before execution resumes.

### A performance-first implementation sequence

1. **Name a workload and metric boundary.** Start with four traces: short loaded prompt, long multi-card prompt, resident decode and over-budget MoE decode; add concurrent serving with TTFT and inter-token constraints. Record cold preparation separately. The repo already has relevant speed, TTFT, server and page counters, so the first task is a coherent ledger rather than a new benchmark that cannot be compared.
2. **Find the largest remaining term in each trace.** Use actual bytes, events and wall times. Compute an optimistic upper bound for removing that term. A 1% launch fraction cannot justify a 20% whole-token prediction. When the stopwatch cannot resolve, use deterministic instructions, bytes, page counts and launches under RULE 1.
3. **Express only the graph facts needed by the first winning candidate.** A stateless-tail row prune needs demand and state-write analysis; a page prefetch plan needs weight-page dependencies and leases; a composer fusion needs producer/consumer and numerical contracts. Grow the common IR from these validated slices rather than requiring every architecture to be graph-converted before a performance experiment.
4. **Trial complete plans under a bounded budget.** Compare against the currently shipped plan on the same model, device, prompt/context distribution and memory ceiling. Count cold cost, peak bytes, traffic, code size, spills, launches and state moves. Use the project's paired/interleaved controls for a performance claim; verify execution and all five principles separately.
5. **Promote by workload and phase.** Preserve distinct legal winners for prefill, decode, short-prompt TTFT and different residency/row classes. Re-plan at safe block/token boundaries as placement changes. The reference BASIC plan remains executable on every supported tier and under a budget below model size.

This view makes the compiler a **constrained request planner**. Its semantic graph is the proof of what may be changed; its cost ledger identifies what is worth changing; the converter prepares portable legal alternatives; the runtime JIT emits and measures the actual kernels; and the server schedule selects among phase-appropriate plans. The output to judge is TTFT and generated-token performance for named workloads, with paging, relocation, generated arithmetic and zero warm allocations still demonstrated by their gates.

## Performance-led model extensibility

Design target: **produce the fastest correct plan jitllm can find for the model, device and workload, while keeping both model additions and optimization experiments small and predictable**. Performance is the primary result; low marginal work to support models and add optimizations shapes the compiler. A class name, weight mapping, default or graph manifest may need to be added at conversion. Models that combine existing operations should use the same runtime graph, generated kernels and optimization recipes as existing models. The compiler should find fast regions in that graph; a successful converter addition must not strand the model on BASIC recipes. Running an unknown-to-jitllm model from a complete verified graph is a required longer-range capability, subject to the performance and extension goals above. It is not a requirement for every intermediate optimization experiment.

### Two extension loops that reinforce each other

**New model:** admit an architecture under RULE 7; bind its weights, defaults and input contract to a checked graph; run generated BASIC lowerings and the available optimized recipes; then measure TTFT and tok/s. A model with a new combination of known operations should not require a parallel host, batch and device executor.

**New optimization:** identify a costly graph region on that model; add a guarded transformation, schedule or generated recipe; compare complete candidate plans on the target device; retain the winner for matching graphs, shapes, formats and residency conditions. The next model with the same semantic pattern inherits the technique without another family implementation. A model may still warrant a narrow optimization: a guard on its actual graph properties and workload is more useful than a guard on its family name.

**Unknown-model target:** given a complete reference export or verified graph, weights and input assets for a class with no jitllm-specific adapter, the generic importer should bind its supported operations and state transitions. The JIT should emit a correct BASIC plan and offer matching optimized recipes. A missing primitive or preprocessing rule requires reusable support. Build and validate this capability as the graph and recipe interfaces mature. If an intake design measurably worsens TTFT, tok/s or the cost of adding models and optimizations, revise that design; unknown-model support does not justify that regression. Weight tensors alone do not reveal the graph, and arbitrary source code may not export successfully. Today RULE 7 still requires the user's decision and the architecture gates before such a model ships.

This makes the ability to **add optimizations** an architectural requirement of the composer, not merely a hoped-for consequence of generic model intake. A proposed technique needs a small, explicit contract:

| Part | What an optimization author supplies |
|---|---|
| Match and legality | A pattern over graph operations, shapes, layouts and state effects; numeric conditions and required backend capabilities. |
| Alternative | A portable graph rewrite, a placement/scheduling choice, or a generated kernel recipe. These are separate interfaces because an offline rewrite and a device kernel make different decisions. |
| Interactions | The values, state effects and layout assumptions read or changed; overlapping matches; required preceding analyses; and analyses or prepared artifacts invalidated by the alternative. |
| Resource bounds | Scratch, page leases, code size, registers, launches and transfers needed to reject impossible candidates before timing. |
| Selection and evidence | The reference plan, bounded candidates, tuning key, whole-region timing and correctness checks that force the chosen path to run. |

Discover alternatives against a versioned graph before selecting a plan. Overlapping matches are competing candidates by default. A combined candidate must explicitly preserve every external consumer and state effect, satisfy a joint numeric/resource contract, and be measured as a complete recipe. For example, a norm shared by two consumers cannot disappear merely because one consumer absorbs it; the other consumer still needs its value or an equivalent generated computation.

Use a bounded pass order: normalize and validate semantics; compute shapes, uses, aliases and effects; enumerate legal rewrites/layouts and recipe matches; select a feasible plan; then lower and measure it. A graph rewrite refreshes the analyses and matches that depend on changed nodes. Keep the validated reference graph and give alternative branches their own identities, so trying one transformation does not silently remove another's input pattern. New matches created by a rewrite can be explored within the same explicit search budget.

Track dependencies from graph and layout versions through recipes, scratch plans, page leases, transfers, emitted kernels and captured command graphs. A layout rewrite invalidates recipes that assumed the old layout and their dependent artifacts. Relocating a block also invalidates affected cross-block fusions, transfers and captures, including those owned by neighboring regions. Recheck guards and rebuild this dependency closure before activating the new plan; retain unaffected artifacts. Candidate identities and tuning records include the relevant transformation versions and layout/shape/device keys.

For example, a newly supported MoE graph may run correctly but spend most decode time gathering expert weights. An experiment could add a recipe for `route -> gather -> expert projection -> combine`, guarded by expert layout, quant format, batch shape and page residency. Its full cost includes page faults and transfers. If it wins, other routed graphs can use it; if it loses under tight memory, the planner retains the existing recipe. The same extension points should accept a page-aware prefetch schedule or an offline layout rewrite when those are the measured bottleneck.

Track **optimization effort** alongside model support effort: files and execution paths touched, backend lowerings added, time to produce a correct candidate, number of distinct graph patterns it covers, and whole-request performance after tuning. A technique that takes a large family-specific patch to try reveals a missing compiler extension point, even if its benchmark wins. That finding should guide the next compiler refactor; it does not invalidate the measured win.

### Measure speed and the cost of a new model together

Set aside model classes before building the compiler. For each one, provide its weights, reference implementation or full graph, tokenizer/input assets and ordinary conversion options. Admit the class under `AGENTS.md` RULE 7, then record every converter, graph, backend and runtime change needed. A successful run has:

1. **Performance as the primary result:** TTFT, single-stream and batched tok/s, cold conversion/attach time, peak memory and bytes/token against strong same-pass baselines on each backend. Report which recipes ran and the remaining whole-request bottleneck. A generic implementation earns use through these measurements, not through a smaller code diff.
2. **Small, explicit model support work:** count added converter mappings/defaults, graph descriptors, reusable ops and runtime family branches. An unfamiliar combination of known ops should need a compact converter description or a verified graph import and no new family branch in the host or device executors.
3. **Cheap targeted optimization:** profile that model, add one guarded technique at the appropriate graph, planner or kernel-recipe level, and report the code touched, other graphs eligible for it and its measured effect. A specialized fast recipe is legitimate when evidence supports it; express its applicability through graph and workload properties where possible.
4. A converter-produced graph with checked weight bindings, explicit state transitions, dynamic-shape guards and a declared input pipeline. `init`, prompt processing and one-step generation must all be captured. The graph and weights enter a portable, pageable JLM container with no precompiled kernel.
5. BASIC generated lowerings for every supported operation on the required CPU and GPU backends, followed by graph-pattern recognition, hardware-specific composition and bounded empirical tuning. Record which executed regions use BASIC recipes and why; prioritize them by their share of TTFT or generated-token time.
6. Values-level comparison against the new model's own reference at nonzero positions, with randomized parameters **and buffers**, routing ties/alternatives where relevant, prompt/decode transitions, batches and real checkpoint prompts. Paging, partial placement, relocation and warm-allocation gates execute, rather than merely being named.

The first held-out set should include an unfamiliar *combination* of existing dense operations, a routed model, a model with a different cache/state transition, and a multimodal or encoder path. Record support as **compact converter addition**, **generic graph import**, **new reusable op**, or **refused with a named missing semantic input**. During the generic-intake milestone, hold out a class with a complete graph and no jitllm-specific adapter, then report correctness, optimized-recipe matches, TTFT, tok/s and implementation cost. Earlier performance experiments do not depend on that milestone. Count runtime family branches and measure the final plan. A differently named Llama clone alone tests too little of either extensibility or optimization.

### The source of truth is executable behavior, not a model-family label

Safetensors and GGUF weights by themselves do not specify a full inference program. A new model needs a trusted source of semantics. These routes have different implementation costs and coverage:

| Intake | What can be automatic | What still has to be checked |
|---|---|---|
| A PyTorch/Hugging Face reference model | A generic exporter captures its computation and weight bindings, then lowers normalized operators and guards to jitllm IR. [TensorRT-LLM AutoDeploy's current support path](https://nvidia.github.io/TensorRT-LLM/features/auto_deploy/support_matrix.html) is a concrete implementation precedent: `torch.export`, dynamic graph pattern matching, KV insertion and GEMM fusion, advertised for supported `AutoModelForCausalLM`/image-text models without an architecture table. | The published validated-model list is narrower than "every model". `torch.export` has shape/control-flow constraints and requires explicit handling of unsupported/custom ops ([PyTorch export](https://docs.pytorch.org/docs/stable/export.html)). jitllm must verify generated decode and state behavior against the source. |
| A publisher-supplied ONNX-like or JLM graph | Import versioned operators, initializers, dynamic shape guards and control-flow regions directly. [ONNX's graph and opset model](https://onnx.ai/onnx/intro/concepts.html) demonstrates framework-independent deployment from a complete graph. | A graph still needs explicit state, tokenizer/preprocessing, quantization and numerical contracts. Custom ops are only names until jitllm can decompose or lower them. |
| Conversion-time reference trace | Capture a reference engine's evaluated graph and tensors for models available as GGUF, then generalize across prompt/decode shapes and data-dependent branches. No reference engine is needed at jitllm runtime. | A few traces cannot prove absent branches or unseen shapes; guards and counterexamples must drive more capture. This is a research route, not a claim that a GGUF tensor table is already sufficient. |

If a generic PyTorch path is built, it should capture an **inference transition**, conceptually `init_state(config)`, `prefill(inputs, state, positions) -> (logits, new_state)` and `step(token, state, position) -> (logits, new_state)`, plus optional encoder/vision functions. It must functionalize observable mutations and aliases so the old and new KV/recurrent states are explicit. [PyTorch export](https://docs.pytorch.org/docs/stable/export.html) can normalize to an ATen graph and offers functionalization, but an ordinary `forward` trace does not automatically define jitllm's paged KV representation or relocation protocol. Those are target-side lowerings of explicit *logical* state. Control-flow and symbolic-shape guards need to survive the export; specializing one example prompt into a fixed path is not model support.

The frontend may execute the model's own code during conversion under an appropriate isolated conversion environment. The resulting JLM carries a validated graph and data; inference does not invoke that Python code. A tokenizer or vision preprocessor with a standard declarative asset can follow its own generic importer. Source-only custom preprocessing needs an equivalent verified input program or an explicit refusal. Otherwise "the model runs" would mean only that a hidden-state function runs on artificial inputs.

### From arbitrary source ops to fast generated recipes

A two-level lowering avoids either extreme of a giant family switch or a permanent slow generic interpreter:

```text
source graph (ATen / ONNX / verified manifest)
      -> versioned core tensor + state/effect IR
      -> canonical graph patterns and legal alternatives
      -> phase/device-specific recipes and placement plan
      -> current runtime CPU emitter and PTX/SPIR-V/MSL IR
```

The **core IR** needs an extensible set of tensor algebra, indexing, reductions, norms, positions, attention/scan patterns, dynamic control and persistent-state effects. Common elementwise expressions can be emitted from expression trees instead of acquiring a new handwritten kernel per activation. Generic indexed/reduction and bounded-loop lowerings provide correct generated code for new *compositions* of known operators. A source custom op should first be decomposed into supported semantics; an irreducible new primitive requires one new **generic op** with a BASIC lowering on each required tier. It must never become `if model_name == ...` or an interpreted Go fallback.

After correctness, the optimizer recognizes subgraphs by **operations, shapes, layouts and effects**: projections, attention forms, gated FFNs, MoE gather/compute/combine, recurrent scans and useful cross-layer producer-consumer chains. Recognition must tolerate different tensor names, weight fusion, harmless views, transposes and equivalent source coding patterns. Each match has a numerical contract and legality guards. It can offer generated variants for fusion, tile layout, reduction, dequant placement, page units and scheduling. The existing composer and auto-tuners then time complete regions on the actual CPU/GPU and row/context classes. A previously unseen model can therefore reach the same optimized recipe as a named model when it contains the same semantic pattern; a novel pattern still gets generated BASIC code and becomes a candidate for further generic optimization.

The converter can precompute device-independent facts and weight layouts, but it cannot choose one GPU's winner for an unknown future machine. The runtime keeps search bounded and caches **timing evidence** under device, driver, compiler version, graph-pattern, shape and quant/layout keys. Reusing a learned choice for a new checkpoint requires a matching cost-relevant key and confirmation if the weights or residency change the result. Repeated blocks make many trials reusable within one new model. The plan remains breakable at block boundaries, so paging, relocation and a different destination device select a new physical plan from the same graph.

### What must change in jitllm's current architecture

| Current seam | Performance-led extensibility target |
|---|---|
| `archOf` and `hfArchTable` decide whether weights have a runnable graph. | Keep an approved class entry and small verified converter mapping where needed. Accept a validated executable graph through a generic importer when available. Neither path should select a family-specific runtime executor. |
| `jlm.Config` and `nn.LayerPlan` encode graph differences as an expanding family feature sheet. | A versioned graph and state-effect contract carry the computation; compact metadata records storage, provenance and shape guards. |
| `forward.go`, batch and device paths reconstruct related graphs separately. | One graph produces several prepared plans for those modes and targets. |
| Composer recipes are attached to named sites. | Give new techniques a pattern, legality/resource contract and candidate-plan interface so one recipe can compete wherever its graph conditions hold. Let offline rewrites and placement schedules use the same checked graph through their own interfaces. |
| New architecture gates are handwritten lists and fixtures. | Generate structural checks where practical, then run the class's independent reference fixture and all required architecture, backend and five-principle gates. |

**Admission rule:** `AGENTS.md` RULE 7 remains in force: a new architecture is a user decision and gets an explicit entry and its required gates. That entry can be small even when the model graph is new; the aim is to avoid duplicating its execution across host, device, batch and decode paths. Generic source import may simplify conversion under that rule. RULE 8's generated BASIC floor, relocation, paging and correctness gates remain mandatory.

**Project-defining demonstration:** add an approved model class with a genuinely different combination of supported operations. Use a small converter adapter or verified graph import, run it correctly across backends and memory budgets, and let the composer/JIT select fast recipes. Measure TTFT, tok/s and preparation cost against strong same-pass baselines. Count the code needed to support it; for known operations, the intended result is a compact converter change and no new family runtime path. Then find a measured bottleneck on that model and add one targeted optimization through a graph rewrite, scheduler or composer recipe. Show its whole-request effect, the code needed to implement it and another eligible graph that can reuse it. A later demonstration must import an approved, previously unknown class from a complete graph without a class-specific adapter and run it through the same optimization pipeline. Evaluate that result against the same performance and engineering-cost measures; the unknown-model capability is achieved only when it coexists with the primary goals.
